# Полный перенос Pi-Star_DV_Dash на Svelte и Go без PHP

Источник требований: клон `Pi-Star_DV_Dash` ревизии `10bf34c9`. Основные проектные инструкции и решение пользователя от 2026-11-26 — в [AGENTS.md](../AGENTS.md). Полный перечень маршрутов, режимов, зависимостей и проверок — в [PARITY.md](PARITY.md). Перенос считается выполненным для **операции**, а не для ссылки или страницы с новым оформлением.

Обязательное ограничение: **в новом дашборде не должно быть PHP совсем**. Этот план заменяет прежний подход с упаковкой PHP-панели. Это план работ, а не заявление о завершённом переносе; текущие классические упаковщики и `compat/` ещё требуют вывода из нового продукта.

## Архитектура

- **Демонстрация** на машине разработки: синтетические ответы, переключение ошибок, проверка всех состояний без передачи в эфир.
- **Raspbian / MMDVM** на `pistar3`: отдельная панель `:8789`, статический Svelte и запросы на своём origin к `/api/status`; источники — `journald`, INI и текущие запуски systemd. Мутации выносятся на HTTPS `:8788` и разрешаются только через типизированный локальный helper. Старую панель `:8787` оставляем доступной при пилоте.
- **Нативная админка**: все разделы доступны на самой плате через Svelte и Go API. Нет PHP docroot, PHP runtime, PHP-прокси, iframe старой админки или зависимости от другого устройства. Сохраняются функции, порядок, значения и условия видимости оригинала; прежний суффикс URL не требует исполнения PHP.
- **Эталон**: `../Pi-Star_DV_Dash` используется только для изучения и независимого сравнения поведения. Если сравнение требует исполнения PHP, эталон запускается на отдельном стенде, не входящем в пакет нового дашборда.
- **Запись**: сервер проверяет авторизацию, CSRF, допустимость операции и ревизию конфигурации; помощник с ограниченными полномочиями сохраняет только нужные файлы, перезапускает затронутые службы и выполняет откат при отказе. Секреты не попадают в публичный API и протоколы испытаний.

## Порядок выполнения и доказательства

1. Начать с инвентаризации и нативной упаковки. Наличие пакета без PHP не означает завершение этапов 3–9.
2. Для каждого раздела последовательно реализовать контракт, системную операцию, Go API, UI, негативные сценарии и проверку через Chromium. Не заменять отсутствующую функцию ссылкой на PHP.
3. Расширять существующие безопасные транзакции и фикстуры; не воспроизводить старые небезопасные shell-вызовы. Зависимости от отсутствующей службы или оборудования указывать явно.
4. Сохранять команду, вывод, код завершения и независимые доказательства в `qa/evidence/`; протокол и имя артефакта — в `docs/TEST-REPORT.md`. Старые PHP-проверки остаются историческими сведениями.
5. После каждого изменения runtime-потока обновлять тематическую Mermaid-диаграмму в `docs/diagrams/`. План не подменяет фактический статус в GitHub Issues.

В таблице перечислены **критерии**, а не утверждения о пройденных испытаниях. CSS-покрытие PHP-страниц и проверки старых обработчиков не засчитываются в перенос. Успешный HTTP 200 не подтверждает сохранение настроек, калибровку, обновление прошивки, восстановление архива или прохождение звука через эфир.
