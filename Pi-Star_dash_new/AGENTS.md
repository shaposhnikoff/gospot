# Задача: полностью повторить старую админку Pi-Star

Это единственный основной файл проектных инструкций. Новые требования, ограничения и уточнения пользователя записывать сюда, не дублировать в родительском `AGENTS.md`.

Инструкции действуют для `/home/max/pi-star-new/Pi-Star_dash_new` и его подкаталогов. Через указатель в родительском `AGENTS.md` они также применяются к связанному Go-бэкенду `/home/max/pi-star-new/panel` и остальным компонентам этого проекта.

## Архитектурное решение: без PHP

- Уточнение пользователя от 2026-11-26: **«В новом дашборде не должно быть PHP совсем»**. Это обязательное требование ко всему переносу.
- Интерфейс реализовать на Svelte/TypeScript, серверные HTTP/API-обработчики — на Go. Существующие ограниченные системные помощники можно использовать; PHP-обработчики и PHP-адаптеры запрещены.
- В исходниках нового продукта и поставляемых артефактах не должно быть PHP-кода. Сборка, установка и работа нового дашборда не должны требовать PHP, PHP-FPM или старого PHP docroot.
- Запрещено заменять перенос оболочкой над PHP, iframe, проксированием PHP-страниц либо ссылками на старую админку или другую плату. Все функции должны работать через собственный интерфейс и API на целевом узле.
- `../Pi-Star_DV_Dash` ревизии `10bf34c9` остаётся неизменяемым внешним эталоном поведения. PHP допустим только в отдельном стенде самого эталона для сравнения; этот стенд не входит в новый продукт, его пакет или обязательный runtime.
- Существующие `compat/`, классические упаковщики и PHP-фикстуры внутри нового проекта — наследие прежнего подхода, подлежащее выводу из нового продукта по плану миграции. Не развивать их как реализацию нового дашборда и не считать их проверки доказательством готовности нативных функций.
- При приёмке проверять состав исходников и пакета, зависимости, unit-файлы и маршруты: PHP отсутствует, операции работают без старого сервера. Наличие всех функций проверять отдельно от отсутствия PHP.
- Это решение заменяет прежнее требование изменять классические PHP-обработчики в `compat/` и упаковывать их вместе с новой панелью.

## Правило: модуль закрывается только зелёными тестами

- Требование пользователя от 2026-11-27, **нарушать нельзя никогда**: по завершении каждого модуля (страницы, раздела, помощника, пакета) написать тесты и проверить **весь** его функционал. К следующему модулю переходить только после того, как все тесты зелёные.
- «Весь функционал» означает: юнит-тесты Go, Python-помощников и фронтенда на каждое правило записи, отказ и откат; сквозную проверку через Chromium на изолированном стенде (`qa/real-write`): открыть → изменить → сохранить → открыть снова с независимой сверкой файлов, прав и перезапусков; затем сборку пакета, `test-deb-entry` и проверку на `pistar3` без вреда для радиочасти.
- Если тест красный — чинить сейчас, а не откладывать. Нельзя объявлять модуль готовым, пропускать проверку «на потом» или переходить к следующему модулю с непроверенным предыдущим. Результаты прогонов сохранять в `qa/evidence/`.

## Внешний вид и скорость

- Уточнение пользователя от 2026-11-27: дизайн оставить **тем же, что в стандартном Pi-Star**, а бэкенд полностью переделать на Go без PHP, и чтобы всё работало быстро. Текущий «карточный» интерфейс не подходит.
- Главная страница, админка и все разделы повторяют разметку, порядок блоков, подписи, цвета и правила раскраски эталона (`index.php`, `mmdvmhost/*.php`, `css/pistar-css*.php`). Отклонения — только для безопасности или работоспособности (например, прокрутка широких таблиц на телефоне).
- Быстродействие: страница опрашивает один JSON-эндпоинт; журналы читаются потоково одним `journalctl -f`, INI перечитываются только при изменении; никаких запусков `grep`/`tail` на каждый запрос.

## Правило: все пути — только в `pistar.conf`

- Требование пользователя от 2026-11-27: пути и параметры, от которых зависят действия с конфигурацией системы, хранятся **только** в файле [`pistar.conf`](pistar.conf) в корне `Pi-Star_dash_new/`. Это пути к бинарникам и скриптам Pi-Star, конфигам радиослужб, справочникам, журналам, маркерам контроллера, имена systemd-юнитов радиослужб, каталоги установки дашборда, порты, целевая плата для деплоя и пути к соседним репозиториям.
- Go-бэкенд (`panel/config.go`, флаг `-config`), Python-помощники (`load_settings()`), `postinst`, `scripts/build-deb`, `scripts/install-release` и тестовые стенды читают значения из этого файла. Зашивать такие пути и адреса в код, скрипты, юниты, `sudoers` или тесты **запрещено**; `sudoers` и drop-in юниты генерируются при сборке. Исключения: сам путь установленного файла `/etc/pistar-dashboard/pistar.conf` и стандартные утилиты ОС (`/usr/bin/sudo`, `systemctl`, `journalctl`).
- Новый путь или параметр сначала добавить в `pistar.conf` с комментарием, затем читать из кода; проверка `panel/config_test.go` загружает репозиторную копию, а `scripts/test-native-runtime.mjs` сверяет её с упакованной.
- Формат: `KEY=value` по строке, `#` — комментарий; без кавычек, пробелов и подстановок, чтобы Bash, Go и Python читали одинаково. На плате файл — conffile пакета (`/etc/pistar-dashboard/pistar.conf`): правки переживают обновление; после правки перезапустить `pistar-panel`, `pistar-wizard`, `psdash-stage`. Root-помощники доверяют файлу, только если его не может изменить никто, кроме владельца-root.

## Раскладка системы и радиослужбы

- Решение пользователя от 2026-11-27: основная раскладка — **как в Pi-Star**: `/etc/mmdvmhost`, `/etc/dmrgateway` и остальные конфиги без `.ini`, бинарники в `/usr/local/bin`, скрипты в `/usr/local/sbin`, справочники в `/usr/local/etc`, файловые журналы в `/var/log/pi-star`, маркеры `/etc/dstar-radio.*`, `/etc/pistar-release`. Дашборд читает и пишет те же файлы, что и оригинал. `pistar3` переводится на эту раскладку; `pistar1`/`pistar2` не трогать.
- Радиослужбы для armhf — готовые сборки Pi-Star из `../Pi-Star_v4_Binaries_Bin` (метка `_PS4`, ARMv6). Им нужны `libwiringPi` и `libArduiPi_OLED`, которых нет в Debian, — поставлять вместе с пакетом. D-Star-часть (`ircddbgatewayd`, `dstarrepeaterd`, `timeserverd`, `starnetserverd`, `remotecontrold`, `timercontrold`) собрана под wxWidgets 3.0 и на Trixie пересобирается из исходников; arm64 — тоже из исходников.
- Скрипты из `../Pi-Star_Binaries_sbin` использовать как есть, если они не трогают PHP и старый дашборд (`HostFilesUpdate.sh`, `pistar-*link`, `pistar-bmapi`/`dapnetapi`/`tgifapi`, `pistar-findmodem`, `pistar-mmdvmcal`, `pistar-modemupgrade`, `pistar-jittertest`, `pistar-factory-reset`, `pistar-firewall`, `pistar-watchdog`, `pistar-remote`, `pistar-keeper`, обработчики `*.service`). `pistar-update`, `pistar-upgrade`, `pistar-daily.cron` и другие скрипты с обращениями к `/var/www/dashboard`, PHP, nginx и `.htpasswd` не ставить; их функции переписать в Go или в собственные скрипты без PHP.
- Пользователь оставляет за собой право переделать любое решение; работать без лишних вопросов и показывать результат на `pistar3`.

## Wi-Fi: два бэкенда

- Решение от 2026-11-27: на `pistar3` (Bookworm) и в целевом образе Trixie сетью управляет NetworkManager, классический `wpa_supplicant.conf` там не действует. Страница Wi-Fi повторяет `wifi.php`, а запись идёт через бэкенд из `pistar.conf`: `WIFI_BACKEND=networkmanager` (профили `nmcli`, PSK передаётся только WPA-хешем) или `wpa_supplicant` (правка блоков файла, root:root 0600). Стенд `qa/real-write --wifi` проверяет бэкенд `wpa_supplicant`.

## Плеер BrandMeister Hoseline

- Требование пользователя от 2026-11-27: встроить его плеер (`shaposhnikoff/hoseline-bm-console-player`) в главную страницу **под Local RF Activity**, только прослушивание одной группы: селектор TG, кнопки Play и Stop. ## Обновление `pistar.conf` на плате

- `pistar.conf` — conffile. Новые ключи из пакета `postinst` дописывает в изменённую вручную копию (`pistar-conf-merge`), существующие строки не трогает; иначе службы не стартуют на неизвестной им конфигурации.

## Реализация и деплой

- Исходный клон `Pi-Star_DV_Dash` оставить эталоном. Переносить его поведение в Svelte/TypeScript и Go, с отдельными ограниченными системными операциями и проверками прав.
- Проверять точный артефакт релиза и указывать его имя в отчёте. `release-VxoR4M` — исторический PHP-пакет, не целевой релиз нового дашборда. Новый пакет без PHP собирать при изменении продукта; изменение только теста или отчёта не требует пересборки. Проверку свежей нативной сборки не приписывать старому релизу.
- Для пилотного деплоя использовать тестовую `pistar3` (`192.168.210.194`). На ней раздельны панель оператора `:8789` и HTTPS-админка `:8788/manage/`. Проверить установленные файлы, доступность страниц и сохранность радио-INI и запущенных радиослужб. Не выдавать деплой нативной части за установку полной админки.
- Прогоны с записью, отказами и откатами выполнять на изолированных фикстурах. Не менять рабочие Raspberry ради теста и не собирать образ ОС для проверки дашборда.

## Образ ОС

- Решения пользователя от 2026-11-27: нужна полная система сборки образа на **Raspberry Pi OS Trixie (Debian 13)**, которая ставит пакет `pistar-dashboard` штатно через `.deb`, а не копированием бинарника.
- Архитектуры: сначала **armhf** (ARMv7+), это основная цель. Все три платы — Raspberry Pi 2 Model B; Rev 1.1 (`pistar1`, `pistar3`, BCM2836 Cortex-A7) только 32-битные и arm64 не запускают. **arm64** (Pi 3/4/5/Zero 2W) — второй этап, после рабочего armhf-образа. Пакеты строить так, чтобы архитектура была параметром сборки.
- В образе — **полный набор радиосервисов Pi-Star** (MMDVMHost, DMRGateway, YSF/P25/NXDN/DAPNET Gateway, ircDDBGateway, D-StarRepeater и др.), каждый отдельным `.deb` из закреплённых ревизий исходников.
- Сборка образа **пока только локально** (Docker + pi-gen). В GitHub Actions образ не собирать; CI продолжает собирать только `.deb`.
- Запрет «не собирать образ ОС для проверки дашборда» остаётся: образ — отдельный продукт, проверки дашборда выполняются на фикстурах.

## Как проверять

- Уточнение пользователя от 2026-11-26: ссылки локального превью на `8788` вели в другое приложение. Не считать штатный номер порта доказательством доступности Pi-Star. Запускать изолированную админку, передавать фактические порты в runtime и проверять в Chromium переход из каталога в редактор и обратно; чужие процессы на занятых портах не трогать.
- Локальное превью, открытое через перенаправленный адрес Codex (например, `localhost:52996`), должно сохранять один origin для каталога, редакторов и API. Внутренние порты стенда не должны попадать в браузерные ссылки.
- Досконально тестировать **операции**, а не только наличие страниц. Для редактора пройти штатный путь через Chromium: открыть → изменить → сохранить → заново открыть. Проверить запрос, сессию и CSRF, ответ и сообщение пользователю. Независимо прочитать файл с диска и сравнить с ожидаемым результатом, включая посторонние настройки и права.
- Сверять с оригиналом на одинаковых входных данных. Проверять оба контроллера (MMDVMHost и D-StarRepeater); для условных разделов включать нужную функцию отдельной фикстурой. Проверять интерфейс и навигацию на настольном и мобильном экранах.
- Для нового дашборда использовать настоящий Chromium, реальный Go-бэкенд, штатные помощники и отдельные тестовые systemd-юниты (`qa/real-write`). Исторические сценарии `qa/classic-write` относятся к старому PHP-подходу; нужные проверки переносить на нативный стенд. Сравнение с PHP-эталоном выполнять отдельно, без включения PHP в новый продукт. Питание, обновления и команды радиооборудования на стенде перехватывать с журналированием; для TGIF использовать локальный HTTPS API.
- Проверять успешную запись, невалидные данные, конфликт устаревшей формы, отказ службы, ручной и автоматический откат там, где они применимы. После отклонённой операции проверять, что файлы не перезаписаны и лишние команды не вызваны.
- **Wi-Fi:** на фикстуре с двумя профилями удалять первый через Delete и Save; проверять исходный CSRF, один POST, новый GET, удаление только выбранного блока и сохранение `root:root 0600`. При смене PSK одного профиля независимо рассчитывать WPA-хеш и побайтово сверять второй блок и остальные настройки. Конфликт `wifiRevision` проверять в двух вкладках: второй POST должен показать отказ без повторного `install`; файл должен совпасть с результатом первой записи.
- **Сервисы · DMR:** `qa/real-write/run.sh --services` из `Pi-Star_dash_new/` должен проверить через Chromium изменение Color Code и правила TG, повторное чтение, побайтовую сверку обоих INI, откат и отклонение устаревшей формы. Этот сценарий не заменяет проверку остальных редакторов и сервисов.
