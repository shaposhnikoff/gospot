# Staging on pistar3

From `Pi-Star_dash_new/`:

```sh
./scripts/deploy-pistar3 --server-only  # Keep current UI, or serve a landing page on first install
./scripts/deploy-pistar3                # Install the current dist/ after the final build
./scripts/deploy-pistar3 --release release-VxoR4M  # Deploy the tested operator bundle without rebuilding
./scripts/deploy-pistar3 --rollback     # Switch back to the previous healthy staging release
./scripts/deploy-pistar3 --remove       # Remove the service, account, and all staging releases
```

The SSH destination is fixed at `max@192.168.210.194`. Deployment requires a
trusted host key, key authentication and passwordless sudo. If needed, point
`PISTAR3_SSH_KEY` to an existing private key **outside the dashboard project**.
Only the staging server, its deployment files and (on a full deploy) `dist/`
are transferred. There are no package installs.

Open **http://192.168.210.194:8789/**. `gospot-stage.service` runs as
`gospot-stage`. Only the exact `GET /api/status` fetches data from
`http://127.0.0.1:8787/api/status`; no request headers or query parameters
are forwarded. `GET /runtime.json` is generated by this service; it is not
part of `dist/`. The wizard port advertised in that JSON is `8788`.

Deployment checks the served index, runtime configuration, and status JSON,
and prints the two radio invocation IDs before and after the operation.
Re-running with identical files keeps the running staging process. Rollback
switches the server, unit and UI together; removal is the rollback for the
first installation. Releases are under `/opt/gospot-stage/releases/`.

### Full Configuration and Expert on the same station

On a station with the release's complete `docroot/` served by an authenticated
HTTPS PHP service, set `Environment=GOSPOT_CLASSIC_HTTPS_PORT=<port>` in the
`[Service]` section of a `gospot-stage.service` drop-in. The stage server publishes
only the port in `runtime.json`. The native operator menu constructs HTTPS
links on its own hostname, and forms, sessions and writes stay at the PHP
origin. The public Python status server does not process or proxy writes.
Without this setting the native-only menu retains its original behaviour.

The native `:8788/manage/` service is not a classic PHP endpoint. Deploying
the operator assets alone does not provision a PHP runtime, radio services,
configuration files or permissions. The isolated tests below supply those
dependencies with disposable configurations; the physical pilot remains
native-only.

From the project directory, run `bash qa/classic-write/run.sh
build/release-ctX2Mh/docroot menu-configuration-desktop`. The other cases are
`menu-configuration-mobile`, `menu-expert-desktop` and `menu-expert-mobile`.
Each starts at the release's operator root and exercises its real catalog
and authenticated HTTPS editor in Chromium.
