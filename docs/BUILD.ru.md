# Сборка и тестирование GoSpot

Всё описанное выполняется в клоне репозитория на машине с Linux x86-64 или
arm64. На выходе — два пакета Debian и один образ ОС:

| Артефакт | Чем собирается | Собирается в CI? |
| --- | --- | --- |
| `gospot_<версия>_armhf.deb` (дашборд) | `Pi-Star_dash_new/scripts/build-deb` | да |
| `gospot-radio_<версия>_armhf.deb` (радиоплатформа) | `radio/build-deb [bookworm\|trixie]` | нет |
| `gospot-<выпуск>-<арх>.img.xz` (образ ОС) | `image/build.sh` | **никогда** |

Английская версия: [BUILD.md](BUILD.md). Как устроена система:
[ARCHITECTURE.ru.md](ARCHITECTURE.ru.md).

---

## 1. Что должно быть установлено

| Инструмент | Для чего | Примечания |
| --- | --- | --- |
| **Go** | бинарник панели и его тесты | версия из `panel/go.mod`; это единственный Go-модуль в дереве |
| **Node.js 22 и npm** | интерфейс на Svelte, тесты фронтенда, проверки пакета | сначала `npm ci` в `Pi-Star_dash_new/` |
| **Python 3.11+** | root-помощники и их тесты, инструменты радиочасти, стенд QA | сторонние пакеты не нужны |
| **`dpkg-deb`, `dpkg`** | оба пакета | версия проверяется через `dpkg --validate-version` |
| **`qemu-user-static`** | запуск armhf-бинарника на хосте x86 | `scripts/test-native-runtime.mjs` запускает упакованный ARM-бинарник под `qemu-arm-static`; CI ставит этот пакет явно |
| **Docker (rootful)** | библиотеки радиочасти, пересборка D-Star, образ ОС, стенд QA | сборке образа нужны привилегированные контейнеры и loop-устройства |
| **`binfmt_misc` с ARM-записью и флагом `F`** | armhf-контейнеры и сборка образа | `qemu-user-static` / `qemu-user-binfmt` |
| **`openssl`, `sudo`, `visudo`, `socat`, `zip`/`unzip`** | учётные данные, проверка sudoers, релей стенда, тесты засева конфигураций | |
| **Chromium и совпадающий по версии ChromeDriver** | `qa/real-write/run.sh` | `$CHROME_BIN` и `$CHROMEDRIVER` переопределяют автоопределение |
| **~25 ГБ свободного места под `/var/tmp`** | образ ОС | `IMAGE_BUILD_PARENT` |

Пакету радиочасти дополнительно нужны два дерева бинарников Pi-Star рядом с
`Pi-Star_dash_new/`, по путям из настроек (`REFERENCE_BINARIES_BIN_DIR`,
`REFERENCE_BINARIES_SBIN_DIR` — по умолчанию `../Pi-Star_v4_Binaries_Bin` и
`../Pi-Star_Binaries_sbin`). В git-worktree их нужно подключить ссылками. Это
не submodule-и, и обычный клон их не выкачивает.

Первоначальная подготовка:

```sh
git clone --recurse-submodules git@github.com:shaposhnikoff/gospot.git
cd gospot/Pi-Star_dash_new
npm ci
```

## 2. Пакет дашборда (`gospot`)

```sh
cd Pi-Star_dash_new
scripts/build-deb                       # без аргументов и без опций
DEB_VERSION=0.2.0+local.1 scripts/build-deb
```

Скрипт **не принимает аргументов**; единственный вход — переменная окружения
`DEB_VERSION`. Без неё версия берётся из строки `Version:` в
`debian/control` (сейчас `0.2.0-1`); CI использует
`${base}+ci.${GITHUB_RUN_NUMBER}`. Версия должна подходить под
`^[0-9][A-Za-z0-9.+~-]*$` и пройти `dpkg --validate-version`.

Что происходит, по порядку:

1. `npm run check` — `svelte-check`, поэтому ошибка типов ломает сборку.
2. `npm run package:native` — `vite build` в `dist/`, затем
   `scripts/package-native.mjs`: он проверяет `dist/`, создаёт
   `build/release-XXXXXX/`, копирует бандл в `release/ui`, пишет
   `ui/runtime.json`
   (`{"backend":"gospot-go","wizardPort":<MANAGEMENT_PORT>}`), приводит режимы
   к `0755`/`0644`, проверяет ещё раз и печатает `Native release: <путь>`.
3. `source ./gospot.conf` — **все пути установки и порты берутся из файла
   настроек**: `DASHBOARD_LIB_DIR`, `DASHBOARD_UI_DIR`, `WIZARD_CONFIG_DIR`,
   `DASHBOARD_BM_STATE_DIR`, `PANEL_PORT`, `MANAGEMENT_PORT`,
   `OPERATOR_PORT`.
4. Кросс-компиляция панели:
   ```sh
   CGO_ENABLED=0 GOOS=linux GOARCH=arm GOARM=7 go -C ../panel build -trimpath \
     -ldflags="-s -w -X main.dashboardVersion=$version" -o "$p$lib/panel" .
   ```
5. Генерация `/etc/sudoers.d/gospot` из `debian/sudoers` подстановкой
   `@DASHBOARD_LIB_DIR@`, режим `0440`, и **сборка прерывается, если остался
   любой `@`** (`unresolved sudoers placeholder`).
6. Генерация трёх юнитов из шаблонов перезаписью `ExecStart`, со
   прерыванием сборки при оставшемся placeholder. Для каждого юнита пишется
   drop-in `50-gospot.conf`; у `gospot-wizard` в drop-in добавляются две
   строки `LoadCredential=` и `StateDirectory=`.
7. Установка семи root-помощников из `../panel/helper/`, файла настроек как
   единственного conffile `/etc/gospot/gospot.conf`, `gospot.conf.default`,
   `gospot-conf-merge`, `gospot-migrate` и дерева интерфейса.
8. `node scripts/audit-native.mjs` — отвергает символические ссылки,
   необычные файлы, любой путь со `classic`, `compat` или `docroot`, файлы
   `.php*`/`.phtml`/`.phar`, байты `<?php`/`<?=` где угодно, `php` в поле
   зависимостей и команды `php-fpm`/`php-cgi`/`php` в юнитах и
   maintainer-скриптах.
9. Запись детерминированного `DEBIAN/md5sums` (conffile намеренно исключён) и
   сборка через `dpkg-deb --root-owner-group`.

Результат и напечатанная SHA-256:

```
Pi-Star_dash_new/build/release-<id>/gospot_<версия>_armhf.deb
```

Проверить собранный артефакт, не устанавливая его:

```sh
bash scripts/test-deb-entry build/release-<id>/gospot_<версия>_armhf.deb
```

Этот скрипт распаковывает пакет через `dpkg-deb -R`, снова запускает
`audit-native.mjs`, а затем `scripts/test-native-runtime.mjs`, который
проверяет, что упакованный `/etc/gospot/gospot.conf` побайтово совпадает с
репозиторной копией, и **запускает настоящий ARM-бинарник под
`qemu-arm-static`**, сверяя побайтово HTML и ресурсы панели оператора,
`/runtime.json`, `404` для `/not-installed.php`, `405` для `POST /`,
перенаправление `/admin/configure.php` →
`https://…:8788/manage/#configuration` и HTTPS-слушатель управления
(анонимно `401`, с Basic `gospot:<пароль>` — `200` с побайтово совпадающими
HTML и ресурсами). Переменная `NATIVE_BROWSER=1` добавляет проход через
браузер.

## 3. Пакет радиоплатформы (`gospot-radio`)

Три скрипта, каждый принимает выпуск Debian как единственный аргумент:

```sh
cd radio
./build-libs.sh  [bookworm|trixie]      # по умолчанию bookworm
./build-dstar.sh [bookworm|trixie]      # по умолчанию bookworm
./build-deb      [bookworm|trixie]      # по умолчанию bookworm; сам вызывает два предыдущих
DEB_VERSION=0.2.0+local.1 ./build-deb trixie
```

`build-libs.sh` собирает три разделяемые библиотеки, которых нет в Debian, но
с которыми связаны бинарники Pi-Star PS4, — `libwiringPi`, `libwiringPiDev`,
`libArduiPi_OLED` — в контейнере `debian:<выпуск>-slim`, запущенном с
`--platform linux/arm/v7`, из закреплённых ревизий (WiringPi, тег 3.14, и
`hallard/ArduiPi_OLED`). ArduiPi_OLED получает явный
`CCFLAGS="-O2 -marm -march=armv6zk -mfpu=vfp -mfloat-abi=hard"`, потому что в
апстриме нет `-marm`, а armhf в Debian по умолчанию собирает Thumb.
Результат: `radio/build/<выпуск>/lib/`.

`build-dstar.sh` пересобирает девять демонов D-Star под **wxWidgets 3.2**
(сборкам PS4 нужен 3.0, которого нет ни в Bookworm, ни в Trixie) в таком же
контейнере с `libwxgtk3.2-dev`. Он подключает `gospot.conf` и закладывает
раскладку только переменными make, без правки исходников: `BUILD=release`,
`CONFDIR=/etc`, `LOGDIR=$GOSPOT_LOG_DIR` и `DATADIR` из
`DSTAR_IRCDDB_DATA_DIR` / `DSTAR_REPEATER_DATA_DIR`. Каждый бинарник
проходит `strip` и проверку `ldd` на неразрешённые библиотеки; сборка падает
при любой. В конце печатаются собранные бинарники и библиотеки `libwx*`, с
которыми связался `ircddbgatewayd`. Результат:
`radio/build/<выпуск>/dstar/{bin,ircddbgateway,dstarrepeater}` и `wx-libs`.

`build-deb` собирает пакет вручную и вызывает `dpkg-deb` — это не исходный
пакет для `dpkg-buildpackage`, и в `radio/debian/` есть только `control` и
`postinst`. Он автоматически запускает две подсборки, если их результатов
нет, подставляет значения из `gospot.conf` в `gospot-rename.table`,
переписывает инструменты Pi-Star, генерирует 27 systemd-юнитов и файлы данных
`paths` и `config-seed`, и прерывается при любом из условий:

* демон D-Star, в котором остался путь Pi-Star, или `dstarrepeaterd`, который
  не пишет в `$GOSPOT_LOG_DIR` (обход — `GOSPOT_ALLOW_STALE_DSTAR=1`, только
  для изучения);
* юнит, названный в настройках, но не устанавливаемый пакетом;
* ключ настроек, нужный файлу `paths`, но отсутствующий в `gospot.conf`;
* член `config_clean.zip` без соответствующего ключа `CONF_*` или такой,
  который таблица переименований не может переписать;
* любой файл `*.php`, любое имя файла с `*pistar*`/`*pi-star*` или любое
  текстовое вхождение `pistar`/`pi-star`/`pi_star`, которое таблица не
  переименовывает и не разрешает явно.

Результат и напечатанная SHA-256:

```
radio/build/<выпуск>/gospot-radio_<версия>_armhf.deb
```

Обратите внимание: аргумент выпуска проверяют только `build-libs.sh` и
`build-dstar.sh`; `build-deb` использует его лишь как часть пути
`build/<выпуск>`. `trixie` принимается везде, но в CI не прогоняется.

## 4. Образ ОС

```sh
./image/build.sh                                 # пакеты + образ + офлайн-проверка
./image/build.sh --prepare-only                  # пакеты + контекст pi-gen, без сборки в Docker
./image/build.sh --arch armhf                    # явная архитектура (по умолчанию IMAGE_ARCH)
RADIO_DEB=… DASHBOARD_DEB=… ./image/build.sh     # использовать уже собранные пакеты
BUILD_PARENT=/srv/build ./image/build.sh         # переопределить IMAGE_BUILD_PARENT
```

Опции — ровно так, как их печатает сам скрипт:

* `--arch ARCH` — архитектура образа, по умолчанию `IMAGE_ARCH` из настроек.
  Сейчас поддержан только `armhf`; `arm64` завершается с объяснением (сначала
  нужны закреплённый коммит ветки `arm64` в pi-gen и arm64-пакеты).
* `--prepare-only` — выкачать pi-gen, собрать пакеты и подготовить контекст
  Docker, затем остановиться и напечатать команду для завершения вручную.
* `--help` / `-h` — текст подсказки.

Окружение: `RADIO_DEB` и `DASHBOARD_DEB` указывают на уже собранные пакеты
вместо их сборки (скрипт сверяет у каждого поля `Package` и `Architecture` с
`RADIO_PACKAGE`/`DASHBOARD_PACKAGE` и запрошенной архитектурой);
`BUILD_PARENT` переопределяет `IMAGE_BUILD_PARENT`, причём сборка отказывается
работать, если родительский каталог находится внутри репозитория или путь
содержит пробелы.

Каждый путь, имя, порт и закреплённая ревизия берутся из файла настроек,
указанного в `image/settings.path` (сейчас `Pi-Star_dash_new/gospot.conf`):
`IMAGE_NAME`, `IMAGE_SUITE`, `IMAGE_ARCH`, `IMAGE_HOSTNAME`,
`IMAGE_DEFAULT_PASSWORD`, `IMAGE_ENABLE_UNITS`, `IMAGE_ENABLE_CLOUD_INIT`,
`IMAGE_COMPRESSION`, `IMAGE_MASK_UNITS`, `IMAGE_FIRSTBOOT_*`,
`BOOT_CONFIG_TXT`, `BOOT_CMDLINE_TXT`, `IMAGE_PIGEN_REPO`,
`IMAGE_PIGEN_REV_ARMHF`, `IMAGE_BUILD_PARENT`,
`IMAGE_BUILD_RASPBIAN_MIRROR`, `RADIO_PACKAGE`, `DASHBOARD_PACKAGE`.
*Установленный* путь файла настроек читается из `conffiles` самого пакета
дашборда.

**Куда попадает результат.** Каждый запуск создаёт
`$IMAGE_BUILD_PARENT/<IMAGE_NAME>-build.XXXXXXXXXX/` (по умолчанию под
`/var/tmp`, вне репозитория). Внутри, в `pi-gen/deploy/`, лежат:

* `<образ>.img.xz` — сжатый образ;
* `<образ>.img.xz.sha256`;
* `<образ>.manifest` — репозиторий и коммит pi-gen, выпуск и архитектура,
  коммит исходников (с отметкой, если рабочий каталог был грязным), а также
  имя, версия, SHA-256 и имя файла каждого пакета;
* журналы сборки pi-gen.

В сборочном каталоге также остаются `radio-build-deb.log` и
`dashboard-build-deb.log`, если пакеты собирались здесь же, и тот же
`manifest`. Закреплённые коммиты фиксируют *входные данные*; пакеты
Raspberry Pi OS, ядро и прошивка берутся из живого архива, поэтому две сборки
из одних исходников не побайтово одинаковы — храните манифест и SHA-256 вместе
с релизом.

### Проверка образа

Первую из этих команд `build.sh` выполняет сам:

```sh
image/verify-artifact.sh ОБРАЗ RADIO_DEB DASHBOARD_DEB
image/qemu-boot.sh ОБРАЗ [ЧИСЛО_ПЛАТ]
```

`verify-artifact.sh` — **офлайн**-проверка: он подключает корневой и
загрузочный разделы только для чтения через loop-устройство (нужен `sudo`) и
изучает их с хоста, запуская `visudo`, `dpkg` и `ldd` *внутри* образа через
qemu-user. Среди прочего он проверяет: оба пакета установлены в ожидаемых
версиях и их файлы совпадают с `md5sums`; `IMAGE_ENABLE_UNITS` включены, а все
радиоюниты **не** включены; `IMAGE_MASK_UNITS` замаскированы; нет пакетов и
файлов PHP, nginx и php-fpm и нет `/var/www/dashboard`; нет имён файлов
Pi-Star, а упоминания Pi-Star встречаются только там, где это разрешает
таблица переименований; нет учётных данных управления, нет маркера первого
запуска, нет ключей хоста SSH и нет закрытых ключей под `/etc`, `/home`,
`/root`, `/var/lib`; сборочное зеркало отсутствует в `/etc/apt`;
`machine-id` не инициализирован; упакованный `gospot.conf` побайтово совпадает
с репозиторной копией и принадлежит root; sudoers разбирается через
`visudo -c`; юнит первого запуска упорядочен до службы управления и
обусловлен своим маркером; имя узла и первый пользователь на месте; все
каталоги из настроек существуют, а у `$GOSPOT_LOG_DIR` режим `775`;
конфигурации радиослужб засеяны; все программы в `$GOSPOT_BIN_DIR`
исполняемы и разрешают свои библиотеки; и `enable_uart=1` без консоли на
последовательном порту.

`qemu-boot.sh` загружает свежие копии образа в QEMU `raspi2b` — это
Raspberry Pi 2 B целевых плат, с собственными `kernel7.img`, деревом
устройств и initramfs образа — внутри одноразового Docker-контейнера и
опрашивает каждую «плату» изнутри этого контейнера, поэтому **на портах хоста
ничего не слушает**. Он проверяет панель оператора (`200`), `/manage/` без
учётных данных (`401`) и с заводскими (`200`), SSH, состояние первого запуска и
состояния юнитов. При двух и более платах он сравнивает отпечатки
TLS-сертификатов и ключей хоста SSH, подтверждая, что у плат, прошитых из
одного образа, нет ничего общего. Он печатает отпечатки, но никогда пароли и
ключи. Ожидание запуска платы может быть долгим; скрипт сдаётся через 60 минут
на плату.

У логики первого запуска есть собственный непривилегированный юнит-тест:

```sh
image/stage-local/01-firstboot/tests/test_firstboot.sh
```

## 5. Наборы тестов

Канонический список — тестовый шаг CI. Из `Pi-Star_dash_new/`:

```sh
npm ci
npm test
go -C ../panel test ./...
python3 -B -m unittest discover -s ../panel/helper
debian/test-gospot-conf-merge.sh
debian/test-gospot-migrate.sh
../radio/test_seed_configs.sh
python3 -B -m unittest discover -s ../radio -p 'test_gospot_*.py'
```

### Go

```sh
cd panel
gofmt -l .            # не должен печатать ничего
go vet ./...
go test ./...
```

`panel/` — единственный Go-модуль. `panel/config_test.go` загружает
репозиторную копию `gospot.conf`, поэтому ключ, добавленный в код, но не в
файл настроек, падает здесь. Бенчмарки лежат в
`panel/configure_bench_test.go`.

### Python-помощники с правами root

```sh
env -u GOSPOT_SETTINGS python3 -B -m unittest discover -s panel/helper
```

`GOSPOT_SETTINGS` нужно явно сбросить: помощники учитывают эту переменную при
запуске не от root, и оставшееся в оболочке значение направило бы тесты на
чужой файл настроек. Набор покрывает `gospot-configure` (чтение, план,
применение, откат, редакторы отдельных файлов, резервное копирование и
восстановление, заводской сброс, CSS Tool и оба бэкенда Wi-Fi),
`gospot-config`, `gospot-calibrate`, а также пути служб и протоколов DMR.
Ни root, ни сеть, ни systemd не нужны — тесты подменяют `systemctl` и работают
на временных фикстурах.

### Пакет радиоплатформы

```sh
radio/test_seed_configs.sh
python3 -B -m unittest discover -s radio -p 'test_gospot_*.py'
```

У `test_seed_configs.sh` нет shebang (первая строка — `set -euo pipefail`),
поэтому запускайте его как исполняемый файл или через `bash`; нужны `zip` и
`unzip`. Он собирает собственный архив-фикстуру и доказывает, что
отсутствующие конфигурации создаются с режимом `0644` и переписанными
Pi-Star-строками, что неизвестный путь Pi-Star отвергается и файл не
устанавливается, что существующий файл остаётся побайтово и по режиму
неизменным, что перечисленный, но отсутствующий в архиве член пропускается, и
что повторный запуск ничего не меняет.

Python-наборы покрывают `gospot-watchdog`, `gospot-remote`, `gospot-rebrand`
и `gospot-radio-migrate`. Два набора для демонов запускают настоящий демон и
его настоящий обработчик как подпроцессы с подменённым `systemctl`, поэтому
root не нужен. Два теста `gospot-rebrand` пропускаются, если деревья
бинарников Pi-Star не выложены рядом с репозиторием.

### Shell-тесты дашборда

```sh
cd Pi-Star_dash_new
```

Как устроена изоляция — и, значит, что означает результат:

* **Выделенная сеть Docker `--internal`** и контейнер на каждый запуск,
  собранный из `qa/real-write/Dockerfile` (`debian:bookworm-slim` плюс
  `python3` и `sudo`, с системными пользователями `gospot-wizard` и `mmdvm`),
  с ограничением числа процессов. Внутренняя сеть не публикует портов, поэтому
  релей на `socat` перебрасывает сырые байты TLS на loopback — TLS и
  аутентификация по-прежнему терминируются на настоящем Go-сервере.
* **Никакой системной шины хоста.** Заглушка `systemctl` внутри контейнера
  общается через один смонтированный Unix-сокет с `qa/real-write/bridge.py` на
  хосте, который принимает только `(dmrgateway|mmdvmhost).service (ok|fail)` и
  перезапускает лишь два одноразовых юнита `systemd-run --user` этого запуска.
  Отказ создаётся тем, что тестовая служба завершается с ненулевым кодом, а
  восстановление требует подтверждения от самого systemd.
* Файлы конфигурации — копии INI-фикстур из
  `image/stage-mmdvm/00-install/files/` с тестовыми идентификаторами,
  владелец `mmdvm:mmdvm`. Учётные данные генерируются на каждый запуск.
* Используются только настоящие артефакты: интерфейс либо собирается заново,
  либо берётся из релиза, переданного через `--dist`; Go-бинарник
  кросс-собирается из `panel/`; четыре помощника копируются из
  `panel/helper/` и **сверяются по SHA-256 внутри контейнера**; файл sudoers
  генерируется из `debian/sudoers` и проверяется через `visudo -c`.
* Проверки не зависят от интерфейса: оба радио-INI сравниваются побайтово с
  отдельно построенным эталоном, история перезапусков читается из собственного
  журнала событий контейнера, и проверяется отсутствие остатков
  `previous.json`/`pending.json`.

Доказательства — строки `PASS …` на stdout вместе с применёнными
SHA-256-дайджестами, строкой проверки хешей интерфейса, строкой кода
HTTPS-ответа и результатами systemd по каждому перезапуску. При сбое скрипт
выводит результаты служб и журнал службы, а Python-обвязка печатает страницу и
консоль браузера. Всё временное удаляет обработчик `EXIT` (контейнеры, сеть,
пользовательские юниты и рабочий каталог); Docker-образ стенда сохраняется,
чтобы повторный запуск был быстрым.

Требования: Docker, Go, npm с локальными зависимостями, Chromium и
совпадающий по версии ChromeDriver, Python 3, OpenSSL, `socat` и работающий
`systemctl --user` под Linux. Первому запуску нужен доступ к пакетам Debian,
чтобы собрать контейнер.

## 6. CI

`.github/workflows/deb-release.yml`, *Build and publish GoSpot Bookworm deb*,
запускается **на каждый push** (`on: push`, любая ветка или тег; задание
сборки пропускается при удалении ветки). Права верхнего уровня —
`contents: read`.

Задание `build` на `ubuntu-24.04` делает checkout без submodule-ей и без
сохранения учётных данных, настраивает Node 22 (кеш npm по
`Pi-Star_dash_new/package-lock.json`) и Go из `panel/go.mod`, выполняет список
тестов из §5, ставит `qemu-user-static`, собирает пакет дашборда с
`DEB_VERSION="${base}+ci.${GITHUB_RUN_NUMBER}"`, проверяет, что получился
ровно один `gospot_*_armhf.deb` с ожидаемыми `Version` и `Architecture`,
запускает на нём `scripts/test-deb-entry` и выгружает `.deb` вместе с
`SHA256SUMS` как артефакт `bookworm-armhf`.

Задание `release` скачивает артефакт, повторно проверяет `sha256sum -c` и
публикует его в GitHub Releases под тегом этого запуска
`deb-<номер запуска>-<первые 12 символов коммита>` — создавая релиз или
перезаписывая файлы с `--clobber`, если тот же тег используется повторно.

Таким образом CI собирает и публикует **только пакет дашборда**: один `.deb` и
один `SHA256SUMS` на коммит. Пакет `gospot-radio` в CI не собирается (ему
нужны деревья бинарников Pi-Star и armhf-контейнеры Docker), а **образ ОС в
CI не собирается никогда** — это отдельный продукт, который собирается
локально, а проверки дашборда выполняются на фикстурах. В самих релизах лежат
оба пакета, образ ОС, контрольные суммы и описание изменений на двух языках.

## 7. Деплой релиза на плату

Поддерживаемый путь устанавливает **опубликованный проверенный пакет** — без
синхронизации исходников и без пересборки на плате:

```sh
cd Pi-Star_dash_new
scripts/install-release deb-<номер запуска>-<12 символов коммита>
```

Тег должен соответствовать `^deb-[0-9]+-[0-9a-f]{12}$`. Скрипт скачивает
`SHA256SUMS` и единственный `.deb` из релиза GitHub, требует, чтобы список
файлов состоял ровно из одной строки, проверяет дайджест, сверяет поля
`Package` и `Architecture` пакета, печатает тег релиза и SHA-256 и передаёт
пакет по SSH на `DEPLOY_HOST` из настроек (`pistar3`) с `BatchMode=yes` и
`StrictHostKeyChecking=yes`.

На плате он проверяет имя узла и архитектуру, делает снимок **до** (SHA-256,
владелец, группа и режим обоих радио-INI плюс `InvocationID` у
`mmdvmhost.service` и `dmrgateway.service`), повторно сверяет хеш переданного
файла, ставит пакет через `sudo -n dpkg -i`, проверяет, что
`pistar-dashboard` больше не установлен (перехват через
`Conflicts`/`Replaces`), выполняет `dpkg -V gospot`, допуская только строку
conffile, проверяет активность `gospot-stage`, `gospot-wizard`,
`gospot-panel`, `mmdvmhost.service` и `dmrgateway.service`, проверяет, что
слушатель управления отвечает `401` без учётных данных с собственным
сертификатом платы, проверяет, что страница оператора побайтово совпадает с
установленным `index.html`, и делает снимок заново, требуя, чтобы он не
изменился:

```
PASS package installed: operator bytes match; both radio INIs, ownership,
     modes and InvocationIDs unchanged
```

Остальные скрипты в дереве — вспомогательные для разработки, а не пути
релиза, и каждый об этом говорит: `panel/deploy.sh` и
`panel/deploy-wizard.sh` ставят свежесобранный бинарник и сгенерированный
юнит на фиксированную пилотную плату (см. `panel/README.md` и
`panel/WIZARD.md`); `scripts/release-pistar3` объединяет проверки, сборку и
оба этих скрипта; `scripts/deploy-pistar3` управляет Python-сервером staging
под `/opt/gospot-stage/` и не ставит никакого пакета. Перевод платы с
апстрим-раскладки радиочасти на раскладку Pi-Star — это
`radio/migrate-board <gospot-radio_*.deb>`, который делает резервные копии,
имеет откат через `trap … ERR` и до объявления успеха проверяет баннер модема
и вход в мастер DMR.

Не выдавайте деплой нативной части за установку полной админки и не меняйте
работающую Raspberry ради теста — прогоны с записью, отказами и откатами
выполняются на изолированных фикстурах.

## 8. Правила, которые должен соблюдать участник

1. **Никакого PHP.** Ни в исходниках, ни в пакетах, ни в зависимостях, ни во
   время работы; ни один шаг сборки или установки не должен требовать PHP,
   PHP-FPM или старого PHP docroot. Перенос нельзя заменить оболочкой вокруг
   PHP, iframe, проксированием PHP-страницы или ссылкой на старую админку либо
   другую плату — каждая функция должна работать через собственный интерфейс и
   API GoSpot на целевом узле. `Pi-Star_DV_Dash` ревизии `10bf34c9` остаётся
   неизменяемым внешним эталоном; он не входит в продукт, его пакет и
   обязательный runtime. Это проверяют `scripts/audit-native.mjs`,
   собственные проверки сборки радиопакета и `image/verify-artifact.sh`.
2. **Пути — только в `gospot.conf`.** Новый путь, порт или параметр
   **сначала** добавляется в `Pi-Star_dash_new/gospot.conf` с комментарием, и
   только потом читается из кода. Зашивать такие значения в код, скрипты,
   юниты, `sudoers` или тесты запрещено; `sudoers` и drop-in юниты
   генерируются при сборке. Исключения — только путь самого установленного
   файла настроек и штатные утилиты ОС. `panel/config_test.go` загружает
   репозиторную копию, а `scripts/test-native-runtime.mjs` сверяет её с
   упакованной. Формат остаётся строгим: `KEY=value` по строке, `#` —
   комментарий, без кавычек, пробелов и подстановок, чтобы Bash, Go и Python
   читали файл одинаково. После правки файла на плате перезапустите
   `gospot-panel`, `gospot-wizard` и `gospot-stage`; новый ключ дописывается в
   изменённый вручную conffile через `gospot-conf-merge` при обновлении.
3. **Модуль закрывается только зелёными тестами.** Когда страница, раздел,
   помощник или пакет готов, напишите тесты и проверьте **весь** его
   функционал, прежде чем идти дальше: юнит-тесты Go, Python-помощников и
