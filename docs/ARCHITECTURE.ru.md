# Архитектура GoSpot

GoSpot — совместимая с Pi-Star панель хотспота и радиостек **полностью без
PHP**: интерфейс на Svelte 5 и TypeScript, все HTTP- и API-обработчики на Go, а
те немногие операции, которым нужен root, выполняют небольшие проверяемые
помощники на Python и Bash, вызываемые через `sudo`. На плате панель читает и
пишет те же файлы, что и классический Pi-Star (`/etc/mmdvmhost`,
`/etc/dmrgateway`, `/usr/local/bin`, `/usr/local/sbin`, `/usr/local/etc`,
`/etc/dstar-radio.*`), поэтому оператор находит те же меню, страницы, поля и
кнопки, что и раньше.

Английская версия: [ARCHITECTURE.md](ARCHITECTURE.md). Сборка и тесты:
[BUILD.ru.md](BUILD.ru.md).

## 1. Состав репозитория

| Каталог | Что внутри |
| --- | --- |
| `panel/` | Go-бэкенд: один бинарник (`panel`), дающий все три слушателя, и `panel/helper/` — root-помощники с их юнит-тестами |
| `Pi-Star_dash_new/` | Пакет дашборда: исходники Svelte/TypeScript (`src/`), файл настроек `gospot.conf`, упаковка `debian/`, сборочные скрипты `scripts/`, стенды `qa/`, спецификации эталона `docs/` |
| `radio/` | Пакет `gospot-radio`: радиобинарники, обработчики служб, systemd-юниты, Python 3-порты `gospot-watchdog`/`gospot-remote`, инструменты переименования и миграции |
| `image/` | Сборка образа Raspberry Pi OS (стадии pi-gen, первый запуск, проверка, загрузка в QEMU) |
| `.github/workflows/` | CI, собирающий и публикующий `.deb` дашборда |
| `Pi-Star_DV_Dash/` | Неизменяемая классическая PHP-панель, ревизия `10bf34c9` — только эталон поведения. В продукт, его пакет и runtime не входит |

На плату ставятся два пакета Debian:

* **`gospot`** — дашборд (Go-бинарник, ресурсы интерфейса, помощники, conffile
  настроек, sudoers, три юнита). Заменяет `pistar-dashboard`.
* **`gospot-radio`** — радиоплатформа (демоны, инструменты, юниты, библиотеки,
  которых нет в Debian). Заменяет `pistar-radio` через
  `Provides`/`Replaces`/`Conflicts`.

## 2. Файл настроек — единственный источник путей

`Pi-Star_dash_new/gospot.conf`, установленный как conffile
`/etc/gospot/gospot.conf`, — **единственное** место, где хранятся пути к
бинарникам и скриптам, конфигам радиослужб, справочникам, журналам, маркерам
контроллера, имена systemd-юнитов, каталоги установки, порты, целевая плата для
деплоя и пути к соседним репозиториям. Зашивать такие значения в код, скрипты,
юниты, `sudoers` или тесты запрещено; `sudoers` и drop-in юниты *генерируются из
настроек при сборке пакета*. Исключения — только путь самого установленного
файла настроек и штатные утилиты ОС (`/usr/bin/sudo`, `systemctl`,
`journalctl`).

Формат намеренно сделан пересечением того, что одинаково читают Bash `source`,
Go и Python: `KEY=value` по строке, `#` начинает строку-комментарий, без
кавычек, пробелов и подстановок. Значения времени выполнения — чистые
абсолютные пути.

Его соблюдают три независимых читателя:

* **Go** — `panel/config.go`. `readSettings` отвергает ключ, не
  соответствующий `[A-Z][A-Z0-9_]*`, значение с пробелом, табуляцией, `"`,
  `'`, `$`, `` ` `` или `\`, и любой дубликат ключа. Затем `applySettings`
  *проверяет каждый ключ, которым пользуется панель*: абсолютные пути, порты
  TCP в диапазоне 1..65535, имена служб systemd по
  `^[A-Za-z0-9@_.-]+\.service$`, допустимые интервалы в секундах, схемы URL и
  завершающий `/`, `RADIO_LOG_SOURCE ∈ {files, journal}`,
  `WIFI_BACKEND ∈ {networkmanager, wpa_supplicant}`,
  `HOSELINE_MAX_LISTENERS ∈ 1..32` — собирает *все* ошибки сразу и отказывается
  стартовать при любой из них. Файл выбирается флагом `-config` (по умолчанию
  `/etc/gospot/gospot.conf`).
* **Python-помощники** — `load_settings()` в `panel/helper/gospot-configure`, с
  той же грамматикой.
* **Shell** — `gospot-jitter` разбирает файл регулярным выражением, а не
  `source`; сборочные скрипты подключают его через `source`.

Важно: root-помощники **доверяют** файлу только если его не может изменить
никто, кроме владельца. `gospot-configure` открывает его с
`O_RDONLY|O_NOFOLLOW` и завершается с `unsafe settings file`, если это не
обычный файл, принадлежащий текущему эффективному uid, без права записи для
группы и остальных. Непривилегированные запуски (тесты) могут указать другой
файл через `GOSPOT_SETTINGS`; под `sudo` от root всегда берётся установленный
путь, так что переменная окружения не может перенаправить привилегированный
запуск.

Поскольку `gospot.conf` — conffile dpkg, локальные правки на плате переживают
обновление пакета. Поэтому новый пакет не может считать, что его ключи есть в
изменённой копии: `debian/postinst` запускает `gospot-conf-merge`, который
**дописывает отсутствующие ключи** и не трогает уже существующие строки. После
правки файла на плате нужно перезапустить `gospot-panel`, `gospot-wizard` и
`gospot-stage`.

## 3. Один бинарник, три слушателя

`panel/main.go` собирает одну Go-программу, которая выбирает роль по флагу;
пакет ставит её один раз в `$DASHBOARD_LIB_DIR/panel` и генерирует три юнита,
различающихся строкой `ExecStart`:

| Юнит | Флаг | Порт | Транспорт | Кому доступен |
| --- | --- | --- | --- | --- |
| `gospot-panel.service` | `-listen :PANEL_PORT` | `8787` | HTTP | двум другим слушателям, loopback |
| `gospot-stage.service` | `-operator-listen :OPERATOR_PORT` | `8789` | HTTP | всем в локальной сети (панель оператора, только чтение) |
| `gospot-wizard.service` | `-admin-listen :MANAGEMENT_PORT -tls-cert … -tls-key %d/tls-key` | `8788` | HTTPS | администраторам, Basic-аутентификация |

### 3.1 Слушатель состояния (`:8787`)

Только он работает с данными радиостека. Он запускает один долгоживущий
обработчик журналов и одну горутину-сборщик с периодом 5 секунд, хранит
неизменяемый снимок `*Status` в `atomic.Pointer` и отдаёт его:

* `GET /api/dashboard` — полный документ дашборда (`panel/dashboard.go`): имя
  узла и позывной, контроллер, режимы и сети, RX/TX, прошивка, состояние линков
  по режимам, таблицы Last Heard и Local TX с разрешёнными именами операторов и
  разговорных групп, палитра CSS Tool, часовой пояс и текущее время. Это
  единственная точка, которую опрашивают все страницы.
* `GET /api/last_heard.php` — классический публичный JSON API, оставленный по
  исходному пути ради совместимости (`panel/legacy_heard.go`).
* `GET /api/status` и `GET /` — сырой снимок в JSON и минимальная встроенная
  страница состояния (`panel/status.html` через `panel/ui.go`), используемые при
  первичном развёртывании. Ответ `503` с `Retry-After: 5` до появления первого
  снимка — нормальное поведение.

Здесь ничего не пишется, и ни одна страница не запускает собственный `grep`,
`tail` или `journalctl`: обработчик журналов и снимок существуют именно для
того, чтобы стоимость загрузки страницы не зависела от размера журналов.

### 3.2 Слушатель оператора (`:8789`)

`panel/operator.go` обслуживает публичную часть. Он намеренно крошечный и
только читает:

* **Белый список методов** — только `GET` и `HEAD`; всё остальное получает
  `405` с заголовком `Allow`.
* **Статические файлы** — `operatorStatic` отображает `/` и `/kiosk` на
  `index.html`, принимает только пути по шаблону
  `^/[A-Za-z0-9_-][A-Za-z0-9_.-]*(/[A-Za-z0-9_-][A-Za-z0-9_.-]*)*$` с известным
  расширением (`.html .js .css .svg .png .ico .woff2 .webp`), раскрывает
  символические ссылки и для корня ресурсов, и для кандидата, отвергая всё, что
  выходит за корень, а также не отдаёт необычные файлы и файлы больше 16 МиБ.
* **Прокси** — `/api/status`, `/api/dashboard` и
  `/api/last_heard.php[?num_transmissions=N]` запрашиваются у
  `http://127.0.0.1:PANEL_PORT` с таймаутом 3 секунды, ограничением тела в
  1 МиБ и *проверкой формы*: ответ дашборда или состояния должен разбираться
  как JSON-объект, ответ Last Heard — как массив; иначе `502`. Ответ `503` от
  слушателя состояния на маршруте Last Heard превращается в пустой массив, а не
  в ошибку, — таблица просто остаётся пустой.
* **Hoseline** — `/api/hoseline` (WebSocket) и `/api/hoseline/groups`.
* **Эксплуатационные точки** — `/health` (проверяет читаемость `index.html`),
  `/metrics` (один счётчик в формате Prometheus), `/runtime.json` (сообщает
  странице порт админки, чтобы номер порта не попадал в бандл).
* **Перенаправления классических URL** — `operatorRedirect` сохраняет старые
  закладки. Публичные страницы сворачиваются в приложение (`/index.php`,
  `/mmdvmhost/lh.php`, `/mmdvmhost/localtx.php`,
  `/mmdvmhost/repeaterinfo.php` → `/`; `/kiosk/` → `/kiosk`). Страницы админки
  перенаправляются *на другой узел*:
  `https://<host>:MANAGEMENT_PORT/manage/<фрагмент>`, например
  `/admin/configure.php` → `…/manage/#configuration`,
  `/admin/expert/` → `…/manage/#expert`. Имя узла берётся из запроса, у него
  отбрасывается порт, и оно отвергается, если содержит `/ \ @ ? #`, CR, LF,
  табуляцию или пробел, — подделанный заголовок `Host` не может увести
  перенаправление в другое место.
* **`/kiosk`** — настенный вид того же одностраничного приложения: порт
  оператора отдаёт тот же бандл, а маршрутизатор фронтенда монтирует для этого
  пути `Kiosk.svelte`.

У каждого ответа есть `Cache-Control: no-store`,
`X-Content-Type-Options: nosniff` и `Referrer-Policy: no-referrer`.

### 3.3 HTTPS-слушатель управления (`:8788`)

`panel/wizard.go` — административная поверхность. Маршруты регистрируются на
`/{$}`, `/manage` и `/manage/`, и `wizardHandler` применяет по порядку:

1. **Обязательный TLS.** `r.TLS == nil` → `503`. Сервер создаётся через
   `ListenAndServeTLS` с `MinVersion: TLS 1.2`.
2. **Наличие пароля.** Хеш читается один раз при старте из
   `$CREDENTIALS_DIRECTORY/admin-password`, который systemd наполняет через
   `LoadCredential=` из `$WIZARD_CONFIG_DIR/admin-password`. Закрытый ключ TLS
   получается так же (`%d/tls-key`), поэтому ни один секрет не является
   аргументом командной строки и не доступен службе по пути. Нет пароля →
   `503`.
3. **HTTP Basic.** Пользователь `gospot` (в классическом Pi-Star был
   `pi-star`), SHA-256 пароля сравнивается через
   `crypto/subtle.ConstantTimeCompare`. При неудаче — `401` с
   `WWW-Authenticate: Basic realm="GoSpot", charset="UTF-8"`.
4. **Разбор маршрута.** Только после двух проверок выше. У каждого обработчика
   в `panel/` стоит комментарий «Dispatch only after wizardHandler's TLS and
   Basic Auth checks» — аутентификация делается один раз, централизованно, и
   обработчики разделов её не повторяют и не ослабляют.

Заголовки каждого ответа: `Cache-Control: no-store`,
`X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` и политика
Content Security Policy. Для API по умолчанию
`default-src 'none'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`.
Для самой страницы приложения (`serveWizardAsset`) она ослаблена до
`default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self'; connect-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`
— `'unsafe-inline'` только для стилей, потому что классическая разметка
раскрашивает ячейки таблиц атрибутами `style`; скрипты остаются
исключительно со своего источника. Когда доступен *Expert > SSH Access*, к
политике добавляется `frame-src http://*:<порт> https://*:<порт>` для клиента
shellinabox, причём порт читается из `SHELLINABOX_DEFAULTS`.

Отдача файлов защищена от обновления пакета прямо во время запроса:
`serveWizardAsset` открывает каталог ресурсов с
`O_RDONLY|O_NOFOLLOW|O_CLOEXEC|O_DIRECTORY`, затем делает `openat` на `assets/`
и на файл относительно этих дескрипторов, так что ни один компонент пути не
может быть символической ссылкой и не может быть подменён под ногами. Имена
бандлов должны соответствовать
`^/manage/assets/([A-Za-z0-9_-][A-Za-z0-9._-]*\.(js|css|png))$`.

### 3.4 CSRF: cookie + заголовок + Origin

`panel/csrf.go` содержит общие проверки запросов к API управления. Запись
принимается только когда выполняется **всё** перечисленное:

* запрос пришёл по TLS (`r.TLS != nil`);
* заголовок `Origin` присутствует ровно один раз и равен `https://` + `Host`
  самого запроса (без учёта регистра);
* cookie `__Host-gospot-csrf` присутствует ровно одна, и её значение — 64
  шестнадцатеричных символа (`archiveHex`);
* заголовок `X-GoSpot-CSRF` содержит то же значение, сравнение —
  `subtle.ConstantTimeCompare`.

`archiveHeader` возвращает значение только если заголовок встречается ровно
один раз, поэтому дублированный `Origin` или `X-GoSpot-CSRF` приводит к отказу,
а не к выбору первого или последнего.

Сам токен создаёт `editorToken` (`panel/services.go`) при первом `GET`
редактора: 32 байта из `crypto/rand`, hex, устанавливаются как
`__Host-gospot-csrf` с `Path=/`, `Secure`, `HttpOnly`, `SameSite=Strict`.
Префикс `__Host-` означает, что браузер примет cookie только по HTTPS, только
для точного имени узла и только с `Path=/`, — её не сможет установить
поддомен или соединение по обычному HTTP. `maintenancePost` оборачивает проверку
для каждого JSON API: CSRF, затем `Content-Type: application/json`, затем
разбор с ограничением размера.

Небольшая встроенная HTML-форма мастера (`GET /` на порту управления)
использует тот же токен как скрытое поле `csrf` с
`Content-Type: application/x-www-form-urlencoded`, ограничением тела 8 КиБ и
той же проверкой единственного `Origin`.

## 4. Модель привилегий

Все Go-службы работают **без привилегий**. `postinst` пакета дашборда создаёт
три системные учётные записи без оболочки входа и без домашнего каталога —
`gospot-panel`, `gospot-wizard`, `gospot-stage` — и проверяет, что ни одна из
них не uid 0. Юниты состояния и оператора добавляют изоляцию:
`NoNewPrivileges=yes`, `CapabilityBoundingSet=` (пустой), `PrivateDevices`,
`PrivateTmp`, `ProtectSystem=strict`, `ProtectHome`, `ProtectKernelTunables`,
`ProtectKernelModules`, `ProtectControlGroups` и ограниченный
`RestrictAddressFamilies` (у юнита оператора есть ещё лимиты по числу
процессов и памяти). Юнит управления работает с `UMask=0077` и получает свои
два секрета только через механизм учётных данных systemd. Только
`gospot-panel` получает `SupplementaryGroups=systemd-journal`, и только чтобы
обработчик журналов мог читать журнал радиослужб.

Больше ничего привилегий не имеет. **Любая запись в систему идёт через
root-помощника, вызываемого как `/usr/bin/sudo -n <помощник> <фиксированный
глагол>`**, а файл sudoers (генерируется при сборке пакета из настроек,
ставится с режимом `0440` как `/etc/sudoers.d/gospot`) перечисляет *точные*
командные строки, а не только имя помощника:

| Помощник (в `$DASHBOARD_LIB_DIR`) | Глаголы, разрешённые в sudoers | Назначение |
| --- | --- | --- |
| `gospot-configure` | `read`, `apply`, `full-read`/`full-write` ровно для `dmrgateway`, `gospot-remote`, `wpaconfig`, `cron`, `rssidat`, `keys-read`, `keys-write`, `backup`, `restore`, `css-write`, `css-reset`, `factory-reset`, `wifi-read`, `wifi-write`, `wifi-scan`, `wifi-action up`/`down`/`reset` | страница Configuration, Expert Full Edit, ключи API, CSS Tool, резервные копии, заводской сброс, Wi-Fi |
| `gospot-config` | `read`, `apply`, `rollback`, `services-read`, `services-apply`, `protocols-read`, `protocols-apply`, `bm-peer` | первичные настройки станции и сети, службы и протоколы DMR |
| `gospot-power` | `reboot`, `shutdown` | страница Power |
| `gospot-native-update` | `start` | страница Update |
| `gospot-modem` | `list`, `flash *` | Expert > FW |
| `gospot-calibrate` | `run`, `restore` | страница Calibration |
| `gospot-jitter` | `run BM`, `run DMR+`, `run HB` | Expert Jitter Test |

Что важно при чтении файла sudoers:

* Глагол — часть разрешённой команды, поэтому `gospot-configure
  delete-everything` не просто не реализован, он не разрешён.
* Правила, через которые идут секреты, помечены
  `NOLOG_INPUT: NOLOG_OUTPUT:`, чтобы журналирование ввода-вывода sudo никогда
  не записывало пароли, PSK или токены API.
* `gospot-modem flash *` — единственная маска, и помощник её закрывает: он
  принимает тип, только если `gospot-modemupgrade list` печатает ровно такую
  строку (`grep -qxF`).
* Шаблон sudoers содержит `@DASHBOARD_LIB_DIR@`; сборка подставляет значение и
  **прерывается**, если остался любой `@` (`unresolved sudoers placeholder`).
  Затем `postinst` выполняет `visudo -cf /etc/sudoers.d/gospot` до включения
  чего-либо.

Каждый помощник сам перечитывает доверенный файл настроек, а не берёт пути от
вызывающей стороны, поэтому скомпрометированная служба дашборда не может
заставить root-помощника работать с другим файлом. Списки аргументов
передаются в `subprocess.run`/`exec` векторами, никогда через оболочку, с
`cwd="/"` и фиксированным `PATH=/usr/sbin:/usr/bin:/sbin:/bin`.

Долгие операции отвязываются от HTTP-запроса: `gospot-power`,
`gospot-modem flash` и `gospot-native-update start` запускают работу через
`systemd-run --unit=<имя>`, так что она переживает запрос, и отказываются
начать второй запуск, пока этот юнит активен (код 3, «already running»).

### 4.1 Проверка ревизии и откат

Транзакционный помощник — `gospot-configure`. Его `read` возвращает
**ревизию**: SHA-256 по короткому имени каждого настроенного файла и его
полному тексту (отсутствующий файл хешируется как литерал `\0missing`), поэтому
ревизия меняется, если какой-либо файл изменился, появился или исчез.

`apply` получает на stdin `{revision, changes, restart, system}` и:

1. берёт исключительный `flock` на `$DASHBOARD_STATE_DIR/configure.lock`;
2. заново снимает состояние файлов и **сравнивает ревизию**; расхождение
   вызывает `Stale`, который печатает `{"error": …, "stale": true}` и
   завершается с кодом **3**. Go-сторона превращает код 3 в `errConfigStale`, а
   HTTP-слой отвечает `409` с текстом «The configuration changed since this
   page was loaded; reload it»;
3. проверяет запрос (`plan`) и вычисляет новый текст каждого целевого файла —
   значения остаются однострочными, а комментарии, порядок ключей, владелец и
   режим сохраняются;
4. вообще отказывается работать, если уже существует
   `$DASHBOARD_STATE_DIR/configure-pending.json`
   (`interrupted operation; inspect private pending backup`), затем записывает
   в этот файл текст каждой цели до изменения, режим `0600`;
5. заменяет каждый файл атомарно: `mkstemp` в том же каталоге, запись,
   восстановление uid/gid и режима исходного файла (`0644` для нового),
   `fsync`, `os.replace`. Файл, который нельзя переименовать поверх
   (bind-монтирование, например `/etc/hosts` в контейнере), перезаписывается на
   месте;
6. выполняет системные операции (имя узла, часовой пояс, маркер контроллера,
   файлы-флаги, пароли, Auto AP, UPnP и т. д.);
7. перезапускает запрошенные юниты, пропуская те, у которых
   `systemctl show -p LoadState` не `loaded`: классическая страница
   перезапускает всё, а на плате просто установлены не все режимы;
8. при **любом** исключении: пишет в журнал только *тип* исключения (никогда
   значение), восстанавливает каждый уже записанный файл в обратном порядке,
   снова перезапускает те же юниты, удаляет файл pending и поднимает
   `operation failed; previous settings restored` (код 2).

Файл pending — намеренный ручной барьер: если помощника убили между шагами 5 и
8, изменения прекращаются, пока администратор не изучит
`configure-pending.json`, не согласует файлы и не удалит его.

Более простой `gospot-config` держится того же принципа в своём варианте: он
блокирует `$DASHBOARD_STATE_DIR`, атомарно заменяет два фиксированных INI,
перезапускает изменённые службы, начиная со шлюза, и хранит последний успешный
содержательный `apply` как снимок, который восстанавливает `rollback`
(успешный откат его потребляет, пустой `apply` его не заменяет). Его снимки и
файлы pending имеют режим `0600`, потому что могут содержать пароли.

Редакторы отдельных файлов используют тот же приём на уровне файла:
`full-read` возвращает `sha256(текст или "\0missing")`, а `full-write`
отвергает несовпадающую ревизию; CSS Tool и оба бэкенда Wi-Fi считают свою
ревизию так же (для NetworkManager — по перечисленным профилям: id, имена,
SSID, тип ключа — и по файлу страны, *никогда* по секретам).

## 5. Как работает запись конфигурации, от начала до конца

Страница Configuration — самая большая поверхность, и она сделана небольшим
каркасом, чтобы каждый классический раздел был одним файлом.
`panel/configure_page.go` задаёт структуры; разделы живут в
`configure_control.go`, `configure_dmr.go`, `configure_dstar_ysf.go`,
`configure_modes.go` и `configure_system.go`, каждый регистрирует
`cfgSectionImpl` с `Order`, функцией `Build` (что показывать; `nil`, если
классическая страница раздел скрывает) и функцией `Apply` (что меняет
отправленная форма). Они следуют `Pi-Star_dash_new/docs/configure-spec/` —
построчной спецификации эталонного `configure.php`.

### Чтение

```
GET /manage/api/configure
  -> readConfigState(run)
       -> sudo -n gospot-configure read
            -> {revision, files{имя→раздел→ключ→значение}, layout, system}
  -> buildCfgPage(ctx)      # Build каждого раздела, в порядке Order
  -> {csrf, revision, sections}
```

`layout` сохраняет порядок внутри файла, чтобы редактор мог показать файл в
том виде, в котором он записан. `system` несёт имя узла, часовой пояс
(читается из символической ссылки `/etc/localtime`), маркеры контроллера и
файлы-флаги.

Результат `read` **кешируется в Go-процессе**, пока у всех наблюдаемых файлов
сохраняется их stat-подпись. `configWatch` собирается из настроек — все ключи
`CONF_*`, `MARKER_*` и `FLAG_*` плюс `HOSTNAME_FILE` — и дополняется
`/etc/localtime`; подпись — время изменения (в наносекундах), размер, режим и
цель символической ссылки каждого пути. Любой глагол помощника, кроме `read`,
сбрасывает кеш. Устаревшая запись кеша не может привести к неверной записи,
потому что `apply` и каждый редактор проверяют ревизию на стороне root.

### Планирование

Отправленная форма превращается в набор изменений функцией `planCfgApply`, и
именно здесь живут два правила, которые делают страницу честной:

1. **Нетронутая форма не пишет ничего.** Применители запускаются дважды: один
   раз на отправленной форме и один раз на *базовой* форме, в которой каждый
   реально отрисованный элемент сброшен к показанному значению
   (`cfgDisplayed`). Всё, что базовый прогон тоже запланировал бы — классические
   значения по умолчанию и нормализации, которые применители ставят при
   *любом* сохранении, — убирается из настоящего плана. Затем `dropStored`
   убирает всё, что уже совпадает с содержимым диска. Итог: открыть страницу и
   нажать *Apply Changes*, ничего не меняя, даёт пустой план, не пишет ни
   одного файла и не перезапускает ни одной службы.
2. **Изменённый файл всё равно получает классические миграции.** Раз файл всё
   равно пишется, в план возвращаются изменения, которые классическая страница
   сделала бы ключам, *уже присутствующим* в этом файле, — например удаление
   старой секции `[aprs.fi]` у YSFGateway, — чтобы файл не остался
   недомигрированным. Значения по умолчанию для *отсутствующих* ключей всё
   равно не добавляются, поэтому минимальная конфигурация остаётся
   минимальной.

Далее `finishCfgPlan` принимает решение о перезапуске. Любое изменение файла
или любая системная операция, кроме «тихих» (`password`, `autoap_psk` —
классические формы пароля и PSK Auto AP не перезапускают ничего), планирует
полный классический список `cfgRadioUnits`: сначала шлюзы и мосты, контроллеры
(`mmdvmhost.service`, `dstarrepeater.service`) последними.

`Apply` раздела может вернуть `cfgError`, что отменяет весь Apply и
показывается оператору как HTTP `422` с этим самым текстом.

### Применение

```
POST /manage/api/configure   {revision, form}
  -> archiveCSRF (TLS + Origin + __Host-gospot-csrf + X-GoSpot-CSRF)
  -> planCfgApply
  -> план пуст?  -> 200 {"ok":true,"changed":[]}             (ничего не делаем)
  -> sudo -n gospot-configure apply  <- {revision, changes, restart, system}
       ревизия не совпала -> код 3 -> 409 «перечитайте страницу»
       ошибка проверки или применения -> код 2, файлы восстановлены -> 422 с причиной
       успех -> 200 {"ok":true,"changed":[…],"restarted":[…]}
```

Go-обёртка даёт записи таймаут 3 минуты и, что важно,
`context.WithoutCancel`: закрытая посреди перезапуска вкладка браузера не
должна обрывать транзакцию. Обработчик управления дополнительно сериализует
работу с конфигурацией через канал на один слот — второй одновременный `apply`
получает `503 «Настройки заняты. Повторите позже.»`, а не вступает в гонку, — а
операции, отличной от чтения, выдаётся бюджет 110 секунд, который переживает
уход клиента.

Резервное копирование и восстановление идут через того же помощника:
`GET /manage/api/backup/classic` отдаёт вывод `backup` как совместимый с
классическим Pi-Star zip с именем
`GoSpot_Config_<узел>_<ГГГГ-Мес-ДД>.zip`, а `POST` принимает не более 256 КиБ
`application/zip` и передаёт их в `restore`. Заводской сброс требует точной
строки подтверждения `RESET`, проверяемой на сервере.

## 6. Источники данных

### 6.1 Чтение журналов

`RADIO_LOG_SOURCE` выбирает один из двух обработчиков, и оба питают *одних и
тех же* потребителей (`journalState` из `panel/journal.go` через
`applyRecord`), так что остальной код не знает, какой используется:

* **`files`** (`panel/logtail.go`, раскладка Pi-Star). MMDVMHost и DMRGateway
  пишут суточные файлы, названные по дате UTC, в `$GOSPOT_LOG_DIR`
  (`FileRotate=1`): `MMDVM-2026-11-27.log`, `DMRGateway-2026-11-27.log`. По
  одному опросчику на файл, с периодом 500 мс: он читает всё, что добавилось
  после прошлого смещения, выделяет полные строки и сохраняет незавершённый
  хвост до следующего раза. При первом подключении он начинает за 512 КиБ от
  конца (и отбрасывает первый, обрезанный, фрагмент); если файл уменьшился или
  был заменён — начинает с нуля. В полночь UTC он сначала дочитывает
  вчерашний файл, а при самом первом подключении читает хвост вчерашнего, чтобы
  история была на месте сразу после полуночи. Отдаются только строки,
  соответствующие `^[A-Z]: ГГГГ-ММ-ДД ЧЧ:ММ:СС.мс `, с разбором метки времени в
  UTC.
  Кроме того, `primeFirmwareFiles` просматривает вчерашний и сегодняшний файл
  целиком (с ограничением 64 МиБ) в поисках последней строки
  `MMDVM protocol version`, потому что она пишется один раз при старте и обычно
  находится далеко выше хвоста, с которого начинается чтение. Это нативный
  аналог классического `getDVModemFirmware()`.
* **`journal`** (`panel/journal.go`). Один долгоживущий `journalctl -f` для
  апстрим-сборок, пишущих в systemd-journald под юнитами `UNIT_MMDVMHOST` и
  `UNIT_DMRGATEWAY`.

Обновление страницы никогда не запускает разбор журнала; на процесс
существует ровно один обработчик.

### 6.2 Разбор Last Heard

`panel/heard.go` и `panel/heard_modes.go` разбирают записи о вызовах по
режимам из прочитанных строк. `DMRSlot.cpp` в MMDVMHost пишет голосовой
заголовок или позднее подключение в начале вызова и заголовок данных (со
счётчиком блоков) для данных; разборщики считают значения справочников внутри
этих сообщений недоверенными и публикуют только ограниченные токены позывного
и ID. `panel/collector.go` принимает событие приложения только в *начале*
записи журнала, а не произвольный текст, вставленный в поиск по ID, полезную
нагрузку MQTT или значение конфигурации. `panel/legacy_heard.go` отдаёт те же
строки в классическом формате JSON `last_heard.php`.

У D-Star свои источники (`panel/dstar.go`, `panel/dstar_links.go`):
ircDDBGateway пишет `Links.log`, `STARnet.log` и `Headers.log` в
`$GOSPOT_LOG_DIR`, и каждый файл разбирается заново только при изменении
размера или времени модификации, причём `Headers.log` — инкрементально.

### 6.3 Списки хостов и база ID

Оба кеша завязаны на *версию файла* — путь, время изменения и размер, — а не на
таймер, потому что `HostFilesUpdate.sh` перезаписывает эти файлы примерно раз в
сутки, а в остальное время они не меняются.

* `panel/hostcache.go` — общий механизм: `cachedHostFile[T]` делает `stat`,
  возвращает кешированный разбор при совпадении версии, иначе разбирает не
  более 8 МиБ функцией, переданной вызывающей стороной. Используется для
  списков разговорных групп `TGList_BM.txt`, `TGList_P25.txt`,
  `TGList_NXDN.txt` и для списков хостов `*_Hosts.txt` по режимам.
* `panel/names.go` занимается `DMRIds.dat`, а это другая задача: около 250 000
  строк. Файл разбирается в точности так, как это делает `CUserDB` в
  MMDVMHost: поля разделяются `,`, табуляцией, CR или LF, поэтому пустые поля
  сохраняют номер колонки; возможна первая строка-заголовок с именами колонок
  (`RADIO_ID,CALLSIGN,FIRST_NAME,…`), иначе колонки 0/1/2; `#` начинает
  комментарий; повторяющийся ID берёт более позднюю строку. Результат хранится
  **без указателей**, чтобы сборщик мусора его не обходил: две целочисленные
  карты (DMR ID → смещение имени, упакованный позывной → смещение имени) над
  одним `[]byte` с именами, записанными с префиксом длины и дедуплицированными.
  Это около 13 МиБ на 250 тыс. ID вместо ~36 МиБ на картах строк. Позывные
  упаковываются в `uint64` по основанию 37 после приведения к верхнему регистру
  и отбрасывания суффикса портативности/SSID или модуля D-Star (`M1ABC/P`,
  `MW0MWZ-1`, `M1ABC  B`). Имена ограничиваются 40 рунами и очищаются от
  непечатаемых символов, потому что файл скачивается из интернета.
  Поскольку повторный разбор занимает заметное время, `backgroundUserDB`
  отдаёт предыдущую таблицу, пока изменившаяся версия разбирается в горутине,
  так что ежедневное обновление справочников никогда не задерживает сборку
  `/api/dashboard`.

`hostNames.target` определяет, что означает адресат строки Last Heard:
`TG nnn` ищется в списке групп режима; для DMR голое число сначала пробуется
как разговорная группа (поэтому 9990 показывается как *Parrot*), а затем как
ID пользователя.

### 6.4 BrandMeister и TGIF

`panel/brandmeister.go` и `panel/links.go` реализуют менеджеры соединений
админки. Управление линками на стороне шлюза (YSF, P25, NXDN, M17, DMR+) идёт
через **UDP-порт удалённых команд** каждого шлюза — то, что делает
классический бинарник `RemoteCommand`, — поэтому таким операциям root-помощник
не нужен вообще. Самообслуживание BrandMeister (статические группы, сброс
динамических, завершение QSO, просмотр peer и профиля) идёт в HTTP API
BrandMeister с ключом из `BM_API_KEY_FILE`; функция `bmNumber` в
`panel/brandmeister.go` допускает, что API присылает числа и как JSON-числа, и
как строки.

`panel/tgif.go` — нативный перенос классических панелей TGIF. Задействованы
две разные службы TGIF, и настройки их разделяют:

* `TGIF_API_URL` (обязательно `https` и с завершающим `/`) — API статических и
  динамических групп. Токен из `TGIF_API_KEY_FILE` отправляется **только** на
  этот URL, как заголовок `Bearer`, никогда не попадает в журнал и никогда не
  входит в ответ.
* `TGIF_SESSION_URL` (с завершающим `/`) — старый менеджер соединений без
  токена, `GET <url><id>/<слот>/<группа>`.

Файлы ключей API лежат в `/etc` с режимом `0600` и владельцем
`DASHBOARD_ADMIN_USER` (`gospot-wizard`) и записываются через
`gospot-configure keys-write`.

### 6.5 Релей Hoseline

Плеер BrandMeister Hoseline находится под *Local RF Activity* и работает
только на прослушивание. Браузер не может сам открыть WebSocket споттера,
потому что споттер проверяет `Origin`, — поэтому ретранслирует плата
(`panel/hoseline.go`):

1. **Токен.** `spotterToken` запрашивает `HOSELINE_PAGE_URL` (с ограничением
   4 МиБ) и извлекает публичный токен, встроенный в страницу. Он ищет
   конструкцию самой страницы `new X("<URL споттера>", token)` — URL споттера
   из настроек экранируется и подставляется в регулярное выражение, — берёт
   идентификатор из этого вызова, затем находит `<идентификатор>="…"` и
   проверяет значение по `^[A-Za-z0-9._~+/=:@-]{1,1000}$`. Токен кешируется на
   15 минут и забывается при отказе рукопожатия, поскольку устаревший токен —
   обычная причина отказа.
2. **Список групп.** `offered` — это собственные группы профиля BrandMeister
   этого хотспота (статические и динамические, читаются из публичного профиля:
   ключ API не читается и не отправляется, и только если DMR включён и имя
   мастера начинается с `BM`; кеш 5 минут, 1 минута после ошибки) плюс
   `HOSELINE_TALKGROUPS`, с удалением дубликатов и сортировкой. Запрошенная
   группа обязана быть в этом списке.
3. **Допуск.** `GET /api/hoseline` требует ровно одного `Origin`, равного
   собственному origin слушателя, ровно одного параметра `tg`, подходящего под
   `^[1-9][0-9]{1,7}$` в диапазоне 91..99999999 и присутствующего в `offered`,
   и свободного слота слушателя. `HOSELINE_MAX_LISTENERS` (1..32) считается
   **для каждой службы дашборда отдельно**, то есть у слушателей оператора и
   управления свои бюджеты, и на каждого слушателя приходится одно исходящее
   соединение. Заполненный релей отвечает `503` с `Retry-After: 30`.
4. **Ретрансляция.** Плата подключается к `HOSELINE_SPOTTER_URL?token=…` с
   origin страницы и подпротоколом `spotter`, отправляет подписку MessagePack
   `[1,[TG]]` и пересылает: тип сообщения споттера `11` → текстовый кадр JSON
   `{"type":"start","source":…}`, `13` → `{"type":"end"}`, `20` → полезную
   нагрузку μ-law как двоичный кадр (не более 8000 байт — одна секунда при
   8 кГц). В обе стороны идёт keepalive-ping каждые 20 секунд и таймаут
   простоя 75 секунд; уход любой из сторон завершает сессию, и браузеру перед
   закрытием сообщается причина кадром `{"type":"error","message":…}`.

Это поддерживают два небольших специализированных кодека, а не зависимость:

* `panel/websocket.go` — RFC 6455 без расширений и без сжатия, только то, что
  нужно релею: `wsUpgrade` для входящих браузеров, `wsDial` для исходящего
  соединения со споттером (клиент маскирует свои кадры), ограничения размера
  сообщения, дедлайн чтения, обновляемый перед каждым кадром, и
  `wsHandshakeError` с кодом отказа, чтобы можно было отличить устаревший
  токен.
* `panel/msgpack.go` — декодер ровно для протокола споттера: целые в `int64`,
  `str` в `string`, `bin` в `[]byte`, массивы в `[]any`, карты в `mpMap`, ext в
  `mpExt`, ограничение глубины 16 и строгое требование, чтобы одно значение
  занимало весь буфер. Кодирование — только `hoselineSubscribe(tg)`.

### 6.6 Сведения о системе и службы

`panel/sysinfo.go` — нативный объём `admin/sysinfo.php`: состояние узла,
память и корневая файловая система, намеренно *без* перечисления произвольных
точек монтирования, без запуска бинарников шлюзов ради баннеров и без
раскрытия адресов и конфигурации шлюзов. `panel/services.go` сообщает
состояние служб через `systemctl show`. `panel/logview.go` и
`panel/maintenance.go` обслуживают Live Logs (чтение хвоста по смещению, по
256 КиБ за порцию; отрицательное смещение означает «начать с текущего конца»,
как делают классические страницы) и страницы Power и Update.

## 7. Фронтенд

Svelte 5 и TypeScript, сборка через Vite (`base: './'`, `target: 'es2022'`,
`assetsInlineLimit: 0`, чтобы ничего не встраивалось и CSP оставалась строгой).
На выходе — обычные статические файлы, которые отдают Go-слушатели; на плате
нет Node.

**Классическая разметка и тема.** Дизайн — стандартный Pi-Star: та же
структура таблиц, порядок блоков, подписи, цвета и правила раскраски, что в
`index.php`, `mmdvmhost/*.php` и `css/pistar-css*.php`. Отклонения допускаются
только ради безопасности или работоспособности (горизонтальная прокрутка
широких таблиц на телефоне). Палитра CSS Tool передаётся **пользовательскими
свойствами CSS**, а не сгенерированными стилями: `panel/theme.go` читает
`$GOSPOT_CSS_FILE` (`/etc/gospot-css.ini`), для любого значения, не являющегося
трёх- или шестизначным hex-цветом, подставляет классическое значение и
публикует девять цветов в `/api/dashboard` как `Theme`; функции
`themeStyle`/`applyTheme` в `src/classic.ts` проверяют каждое значение ещё раз
в браузере и устанавливают на корневом элементе `--ps-page`, `--ps-content`,
`--ps-banners`, `--ps-banner-text`, `--ps-banner-drop`, `--ps-head-drop`,
`--ps-text`, `--ps-even`, `--ps-odd`. `ClassicDashboard`, `GoSpotFrame`,
`Configure`, `Wifi` и `Kiosk` используют только эти переменные, поэтому смена
темы — один пересчёт стилей и никогда не пересборка. Там же лежат классические
правила раскраски ячеек (потери, BER, RSSI, цвета удержания режима) и
построение ссылки поиска по позывному, которая переключается между RadioID и
QRZ по настройке `[Lookup] Service`.

**Маршрутизация.** `src/main.ts` выбирает точку входа по адресу, а
административная часть — **хеш-маршрутизатор**, так что весь интерфейс
управления остаётся одним документом с одним origin:

```
/manage…  -> хеш-маршрутизатор: ''|admin → ClassicDashboard(admin)
                                #logs #power #update #configuration #backup
                                #wifi (и #wifi-conf)
                                #calibration (и #calibration-debug)
                                #expert, #expert-<страница>  → Expert(page)
                                всё остальное                → AdminWorkspace
/kiosk    -> Kiosk.svelte
/#console -> App.svelte
/         -> ClassicDashboard.svelte
```

Каждая страница — динамический `import()`, поэтому код одного маршрута не
скачивается ради другого. Маршрутизатор защищён от гонки медленного импорта с
быстрой навигацией счётчиком поколений и размонтирует предыдущий компонент до
монтирования следующего. `src/routes.ts` — не маршрутизатор, а каталог
операторских назначений, взятый из эталонной панели: каждая запись открывает
*страницу*, но никогда не команду.

**Киоск.** `/kiosk` — полноэкранный настенный экран для телевизора рядом с
хотспотом (1920×1080, 1280×720 и портрет 1080×1920). Он опрашивает
`/api/dashboard` раз в секунду, останавливает опрос на скрытой вкладке и
показывает явное состояние *Connection lost* с восстановлением. В эфире он
показывает позывной, имя оператора, цель с названием разговорной группы,
режим, слот, RF или сеть и живой счётчик длительности, а для RF после
окончания передачи добавляет BER и уровень сигнала; иначе —
*Listening — last call N min ago* и список примерно последних 10 вызовов ниже.
Он использует палитру CSS Tool как акценты, без внешних шрифтов и CDN, без
прокрутки и без подсказок, доступных только при наведении. Поля строк `name` и
`targetName` добавлены для него; существовавшие поля не менялись.

**`classic-entry.ts`** монтирует классическую оболочку в **shadow root**,
чтобы эталонная таблица стилей не протекала в приложение, и только в окне
верхнего уровня.

## 8. Пакет радиоплатформы (`radio/`)

`gospot-radio` обеспечивает раскладку Pi-Star: программы в `$GOSPOT_BIN_DIR`
(`/usr/local/bin`), скрипты и обработчики служб в `$GOSPOT_SBIN_DIR`
(`/usr/local/sbin`), справочники в `$GOSPOT_HOSTS_DIR` (`/usr/local/etc`),
файловые журналы в `$GOSPOT_LOG_DIR` (`/var/log/gospot`), конфиги без суффикса
`.ini` в `/etc` и маркеры контроллера `/etc/dstar-radio.*`.

**Состав.** 21 радиопрограмма PS4, которым не нужен wxWidgets (MMDVMHost,
DMRGateway, шлюзы YSF/P25/NXDN/M17/DAPNET/DGId/APRS, межрежимные мосты,
parrot-ы, MMDVMCal, RemoteCommand, MobileGPS, `teensy_loader_cli`,
`platformDetect.sh`), образы прошивок модема, повторно используемые
`sbin`-инструменты Pi-Star, переименованные в `gospot-*`, три разделяемые
библиотеки, которых нет в Debian (`libwiringPi`, `libwiringPiDev`,
`libArduiPi_OLED`), и архив конфигураций по умолчанию. Дисплеи
(`NextionDriver`, `MMDVMHost_Adafruit`) и обёртки перемонтирования для
apt/dpkg намеренно не поставляются, и не ставится ни один скрипт, который
обращается к PHP, nginx, `.htpasswd` или `/var/www/dashboard`, — их функции
переписаны на Go или в собственные скрипты без PHP.

**D-Star, пересобранный под wxWidgets 3.2.** Демоны D-Star из PS4 собраны под
wxWidgets 3.0, которого нет ни в Bookworm, ни в Trixie, поэтому
`radio/build-dstar.sh` пересобирает девять демонов из закреплённых апстрим-
ревизий в armhf-контейнере Debian: `ircddbgatewayd`, `timeserverd`,
`starnetserverd`, `remotecontrold`, `timercontrold`, `aprstransmitd`,
`texttransmitd`, `voicetransmitd` из `g4klx/ircDDBGateway` (последняя ревизия
до MQTT, в которой ещё есть StarNetServer) и `dstarrepeaterd` из
`g4klx/DStarRepeater`. Исходники **не патчатся**: совместимость с Pi-Star
целиком обеспечивается переменными make — `BUILD=release`, `CONFDIR=/etc`,
`LOGDIR=$GOSPOT_LOG_DIR`, `DATADIR=$DSTAR_IRCDDB_DATA_DIR` или
`$DSTAR_REPEATER_DATA_DIR`, — поэтому `/etc/ircddbgateway` и
`/etc/dstarrepeater` сохраняют формат Pi-Star. Голосовые данные AMBE
(`*.ambe`, `*.indx`) ставятся рядом с демонами, а списки хостов остаются в
`$GOSPOT_HOSTS_DIR`, куда указывают символические ссылки
(`DPlus_Hosts.txt`, `DExtra_Hosts.txt`, `DCS_Hosts.txt`, `CCS_Hosts.txt`,
`XLXHosts.txt`), чтобы ими владел `HostFilesUpdate.sh`. Каждый собранный
бинарник проходит `strip` и проверку `ldd` на неразрешённые библиотеки, а
`build-deb` отказывается упаковывать демон D-Star, в котором остался путь
Pi-Star или чей `dstarrepeaterd` не пишет в `$GOSPOT_LOG_DIR`.

**Обработчики служб и юниты.** Pi-Star управляет демонами через
скрипты-обработчики с именами `<имя>.service` в `$GOSPOT_SBIN_DIR`,
принимающие `start|stop|restart`; GoSpot это сохраняет и оборачивает каждый в
сгенерированный systemd-юнит с тем же базовым именем в `$SYSTEMD_UNIT_DIR`
(`/lib/systemd/system`), у которого `ExecStart`, `ExecStop` и `ExecReload`
вызывают обработчик. Генерируются 23 таких юнита (`mmdvmhost`, `dmrgateway`,
`ysfgateway`, parrot-ы, шлюзы, мосты, `mobilegps`, `ircddbgateway`,
`timeserver`, `timercontrol`, `dstarrepeater`), плюс юниты для двух
Python-демонов, плюс `gospot-hostfiles.service`/`.timer` (ежедневный
`HostFilesUpdate.sh`, через 10 минут после загрузки, со случайной задержкой до
2 часов и `Persistent=true`). **При установке включается только таймер
справочников**; все радиоюниты остаются выключенными — их включает оператор
или `radio/migrate-board`. `RADIO_USER` (`mmdvm`) создаётся как системная
учётная запись в группах `dialout` и `tty` и владеет `$GOSPOT_LOG_DIR` как
группа (режим `0775`).

**`gospot-watchdog` и `gospot-remote`.** `pistar-watchdog` и `pistar-remote`
написаны на Python 2 и не работают на Bookworm и Trixie, поэтому в
`radio/sbin/` лежат их порты на Python 3 без nginx, без `iwconfig` и без
использования оболочки.

* `gospot-watchdog` выполняет проверку каждые 300 с (`--once` — один проход).
  Он держит том журналов заполненным менее чем на 90 %: удаляет
  ротированные `*.1`/`*.1.gz` на верхнем уровне `$SYSTEM_LOG_DIR`, `*.gz`
  старше суток ниже него и `$GOSPOT_LOG_DIR/*.log` старше суток, затем
  обрезает сегодняшний журнал контроллера до 500 строк и перезапускает его. Он
  также перезапускает юнит любого отсутствующего процесса из
  `WATCHDOG_DSTARREPEATER_PROCESSES` (при наличии `MARKER_DSTARREPEATER`),
  `WATCHDOG_MMDVMHOST_PROCESSES` (при наличии `MARKER_MMDVMHOST`) или
  `WATCHDOG_COMMON_PROCESSES` (всегда). Кроме того, он инкрементально
  просматривает журнал DStarRepeater на `Bad DVAP header` и
  `Cannot open the D-Star modem` (перезапуск с долгой паузой, чтобы DVAP успел
  восстановиться) и `No space to write`.
* `gospot-remote` позволяет позывному-смотрителю из `CONF_GOSPOT_REMOTE`
  управлять хотспотом по радио: он следит за журналами, ожидая голосовой
  заголовок DMR на настроенную группу, передачу P25, заголовок D-Star, поле UR
  которого является командой, либо заголовок смотрителя, за которым следует
  подключение к комнате YSF. Команды — `svckill`, `svcrestart`, `reboot`,
  `shutdown`, `hostfiles` для всех режимов плюс `getip`, `wifissid`,
  `wifirssi` и `8ball` для D-Star, которые отвечают медленными данными D-Star
  через `texttransmitd`. Какие юниты затрагивает каждая команда — целиком в
  настройках (`REMOTE_MMDVMHOST_STOP_UNITS`,
  `REMOTE_{DMR,P25,DSTAR,YSF}_RESTART_UNITS` и т. д.). Пауза 30 секунд на
  каждую пару `(режим, действие)` подавляет повторы.

Оба демона используют один укреплённый `load_paths()`: сгенерированный файл
`$RADIO_SHARE_DIR/paths` должен быть обычным файлом, принадлежать текущему
эффективному uid, не иметь права записи для группы и остальных и открывается с
`O_NOFOLLOW`; ключи и значения проверяются заново; переопределение
`GOSPOT_RADIO_PATHS` действует только при запуске не от root.

**Засев конфигураций.** `build-deb` превращает Pi-Star-архив
`config_clean.zip` в список `config-seed` из пар «член архива — цель»,
определяя каждую цель через таблицу переименований и ключи `CONF_*`, и
прогоняет перезапись каждого члена вхолостую, чтобы неизвестная
Pi-Star-строка ломала *сборку*, а не установку. На плате `postinst` запускает
`seed-configs config-seed config_clean.zip rename.table`, который —
**только для отсутствующей цели** — извлекает член архива, перезаписывает его
через `gospot-rebrand apply` и атомарно ставит на место с режимом `0644`.
Существующие файлы никогда не читаются и не трогаются. Засев идёт *после*
`gospot-radio-migrate`, поэтому обновлённая плата сохраняет свою
миграционную конфигурацию, и создаются только действительно отсутствующие
файлы. `/etc/gospot-release` тоже создаётся только при отсутствии.

**Переименование и миграция.** `gospot-rebrand` с таблицей
`gospot-rename.table` (виды правил `tool`, `literal`, `word`, `delete`,
`allow`, `allow-comment`) перезаписывает каждый скрипт и каждую конфигурацию
Pi-Star и **падает на любом вхождении `pistar`/`pi-star`/`pi_star`**, которое
таблица не переименовывает и не разрешает явно. Пути раскладки записаны в
таблице как `${KEY}` и подставляются из `gospot.conf` при сборке, так что сама
таблица не содержит зашитых путей. Намеренно сохраняются: адреса `pistar.uk`
и источники данных, ссылка `mw0mwz.co.uk/pi-star/`, фраза «Pi-Star compatible»
и строки атрибуции в комментариях. `gospot-radio-migrate` переводит плату с
раскладки `pistar-radio` (журналы — поэлементно через `os.rename`, чтобы
сохранились inode, `/etc/pistar-release` → `/etc/gospot-release`, файлы CSS и
remote, ссылки на `/var/log/pi-star` внутри каждого файла `CONF_*`, журнал
смотрителя, генератор MOTD и старые юниты) и **ничего не удаляет**: старый
файл, у которого новое место уже занято, остаётся и о нём сообщается.
`radio/migrate-board` — одноразовый перевод платы с апстрим-раскладки
`MMDVM-Host.ini`/`DMRGateway.ini` с возможностью откатиться: он использует
`convert-config.py`, чтобы получить `/etc/mmdvmhost` и `/etc/dmrgateway` в
формате Pi-Star, делает каталог резервных копий с метками времени,
устанавливает откат через `trap … ERR`, который возвращает старые юниты и
бинарники, и ждёт в цикле проверки и баннера модема, и входа в мастер DMR в
новых журналах.

## 9. Образ ОС (`image/`)

`image/build.sh` собирает образ Raspberry Pi OS Lite локально, с помощью
Docker и закреплённого [pi-gen](https://github.com/RPi-Distro/pi-gen), и
устанавливает два локальных пакета `.deb` *именно как пакеты*
(`apt-get install ./…deb`), чтобы их зависимости разрешались из архива
Raspberry Pi OS. Цель — сначала Trixie (Debian 13) **armhf**, потому что все
три эталонные платы — Raspberry Pi 2 Model B и arm64 не запускают; arm64 —
следующий этап, для него нужны закреплённый коммит ветки `arm64` в pi-gen и
arm64-пакеты. Образ собирается **только локально — никогда в CI**.

Всё, чем пользуются сборка, проверки и первый запуск, берётся из файла
настроек, указанного в `image/settings.path` (сейчас
`Pi-Star_dash_new/gospot.conf`): ключи `IMAGE_*` и `BOOT_*`,
`RADIO_PACKAGE`, `DASHBOARD_PACKAGE` и ключи дашборда и радиочасти.
*Установленный* путь файла настроек берётся из собственных `conffiles` пакета
дашборда, поэтому имена пакетов, юнитов, образа и узла — это настройки, и
переименование продукта пересобирается правкой одних настроек.

**Стадии.** `stage0 → stage1 → stage2` (Raspberry Pi OS Lite, не
экспортируется: создаётся `SKIP_IMAGES`) `→ stage-local`:

| Подстадия | Что делает |
| --- | --- |
| `00-packages` | ставит оба локальных пакета, включает `IMAGE_ENABLE_UNITS` (две панели, служба управления, таймер справочников) и **удаляет учётные данные управления, созданные postinst внутри сборочного контейнера** |
| `01-firstboot` | ставит скрипт первого запуска и его юнит, упорядоченный до `gospot-wizard.service` |
| `02-uart` | `enable_uart=1` в `BOOT_CONFIG_TXT`, отсутствие консоли на последовательном порту в `BOOT_CMDLINE_TXT`, маскировка `IMAGE_MASK_UNITS` |

pi-gen настраивается с `TARGET_HOSTNAME=$IMAGE_HOSTNAME`,
`FIRST_USER_NAME=$GOSPOT_LINUX_USER`,
`FIRST_USER_PASS=$IMAGE_DEFAULT_PASSWORD`,
`DISABLE_FIRST_BOOT_USER_RENAME=1`, `ENABLE_SSH=1` и сохранённым cloud-init
для настройки через Raspberry Pi Imager. Сборка проверяет, что закреплённый
pi-gen действительно по умолчанию собирает запрошенный выпуск и архитектуру, и
переписывает тег Docker-образа и имя контейнера под каждую сборку, чтобы
параллельные сборки не сталкивались. `IMAGE_BUILD_RASPBIAN_MIRROR` может
направить *сборку* на конкретное зеркало Raspbian (некоторые географические
перенаправления подвешивают сборку); хук `export-image` возвращает в готовый
образ собственный источник pi-gen и очищает списки apt, а проверка следит,
чтобы зеркало не осталось в `/etc/apt`.

**Секреты для каждой платы.** Ни один секрет не общий для плат, прошитых из
одного образа. В образе их нет: `00-packages` удаляет то, что создал
`postinst` в контейнере, pi-gen удаляет ключи хоста SSH, а
`/etc/machine-id` остаётся неинициализированным. При первом запуске
`IMAGE_FIRSTBOOT_UNIT` выполняется однажды — с
`ConditionPathExists=!$IMAGE_FIRSTBOOT_DONE`, после появления сети и
**до** службы управления, которая его `Requires=`, — удаляет любые учётные
данные управления из `$WIZARD_CONFIG_DIR` и выполняет тот же код пакета
дашборда, который создаёт *для этой платы* ключ TLS и самоподписанный
сертификат (`CN=<имя узла>`, SAN с именем узла и текущими адресами) и
сбрасывает пароль веб-админки на заводской. Маркер пишется **последним**,
поэтому прерванный первый запуск просто повторится при следующей загрузке.
Ключи хоста SSH заново создаёт Raspberry Pi OS при первом запуске.
Радиоюниты остаются выключенными — ровно как после установки `gospot-radio`.

Входы по умолчанию — классические Pi-Star: SSH и консоль
`$GOSPOT_LINUX_USER` с паролем `$IMAGE_DEFAULT_PASSWORD`, веб-админка —
пользователь `gospot` с тем же паролем. *Configuration > Remote Access
Password* меняет пароль веб-админки и пароль учётной записи Linux вместе и —
как Pi-Star — отказывается принять заводское значение.

Закреплённые коммиты фиксируют **входные данные**, а не результат: пакеты
Raspberry Pi OS, ядро и прошивка берутся из живого архива во время сборки,
поэтому две сборки из одних исходников не побайтово одинаковы. Поэтому сборка
пишет манифест (коммит pi-gen, выпуск и архитектура, коммит исходников и
отметка, был ли рабочий каталог грязным, а также имя, версия, SHA-256 и имя
файла каждого пакета) и `.sha256` рядом с образом; храните их вместе с
релизом.

## 10. Инварианты, которые надо знать до любых изменений

1. **Никакого PHP.** Ни в исходниках, ни в пакетах, ни в зависимостях, ни во
   время работы. Ни iframe, ни прокси, ни ссылка, ни оболочка вокруг
   классической PHP-панели не считаются переносом. `Pi-Star_DV_Dash` — только
   неизменяемый эталон. Это проверяется при сборке (`audit-native.mjs` и
   `find … -name '*.php'` в сборке радиопакета), а проверка образа ищет в
   готовой файловой системе `*.php`, `php-fpm*`, nginx и
   `/var/www/dashboard`.
2. **Пути — только в `gospot.conf`.** Сначала добавить ключ с комментарием,
   затем читать его. `panel/config_test.go` загружает репозиторную копию, а
   `scripts/test-native-runtime.mjs` сверяет её с упакованной.
3. **Одна JSON-точка на страницу, один обработчик журналов на процесс.**
   Никаких `grep` и `tail` на запрос; INI перечитываются только при изменении.
4. **Записи транзакционны.** Чтение → план → применение помощником с проверкой
   ревизии → перезапуск служб, с откатом при сбое. Нетронутая форма не пишет
   ничего; записанный файл никогда не остаётся недомигрированным.
5. **Модуль закрывается только зелёными тестами** — Go, Python-помощники,
   фронтенд, shell-тесты и изолированный стенд на Chromium, который открывает,
   меняет, сохраняет, открывает заново и затем независимо проверяет файлы,
   права и перезапуски. См. [BUILD.ru.md](BUILD.ru.md).
